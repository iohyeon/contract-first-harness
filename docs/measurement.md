# 하네스 효과 측정 절차

이 문서는 하네스(spec-interview, plan-build, plan-verify, plan-execute와 검증 게이트)를 썼을 때와 쓰지 않았을 때를 비교하는 절차를 정합니다. 비용과 품질 신호는 `skills/harness-metrics` 의 `cc-usage.sh` 로 재고, 결함은 게이트 원문과 사람의 판정 기록으로 셉니다.

이 절차로 얻는 결과는 통계가 아닙니다. 기능 2개를 조건을 바꿔 두 번씩 만든 **사례 2건**입니다. 결과를 적을 때도 사례 2건으로 적습니다(아래 "결과 표기 원칙").

## 1. 비교 단위

### 기능 2개

크기가 비슷한 기능 2개(F1, F2)를 고릅니다. 크기는 다음 셋으로 맞춥니다.

| 항목 | 맞추는 기준 |
|---|---|
| 건드리는 파일 수 | 예상치가 서로 1.5배 안쪽 |
| 계약 수 | 새로 정하는 API, DTO, 스키마, 에러 코드 개수가 비슷함 |
| 외부 연동 | 둘 다 있거나 둘 다 없음 |

크기를 맞추지 못했다면 그 차이를 결과 문서 첫머리에 적습니다. 비교를 무르지는 않지만 해석할 때 그 차이를 먼저 의심합니다.

### 쌍 2개와 순서 교차

한 쌍은 실행 2번입니다. 쌍 2개, 실행 4번으로 끝냅니다. 두 번째 쌍에서는 하네스 조건을 기능별로 뒤집어, 기능 자체의 난이도와 실행 순서에서 오는 학습 효과가 한쪽 조건에만 몰리지 않게 합니다.

| 쌍 | 1번째 실행 | 2번째 실행 |
|---|---|---|
| 쌍 1 | F1, 하네스 있음 | F2, 하네스 없음 |
| 쌍 2 | F1, 하네스 없음 | F2, 하네스 있음 |

이렇게 짜면 다음이 성립합니다.

- F1과 F2가 각각 하네스 있음과 없음을 한 번씩 겪습니다. 기능 난이도 차이가 한 조건에 몰리지 않습니다.
- 쌍 1에서는 하네스 있음이 먼저, 쌍 2에서는 하네스 없음이 먼저 실행됩니다. 앞선 실행에서 사람이 익힌 내용(도메인 이해, 저장소 구조, 프롬프트 요령)이 뒤 실행을 돕는 효과가 양쪽 조건에 한 번씩 갑니다.
- 쌍 2의 두 실행은 모두 같은 기능을 두 번째로 만드는 실행입니다. 쌍 1과 쌍 2를 따로 적어 두면 같은 기능을 두 번째로 만들 때 얼마나 줄어드는지도 함께 보입니다.

### 실행 규칙

매 실행은 같은 조건에서 시작합니다.

| 규칙 | 내용 |
|---|---|
| 새 세션 | 실행마다 Claude Code 세션을 새로 엽니다. 이전 실행의 대화, 메모리, 컴팩트 요약을 이어 쓰지 않습니다 |
| 같은 입력 | 기능마다 spec 문서 하나를 미리 써 두고, 두 조건 모두 그 문서만 입력으로 줍니다. 하네스 있음 쪽은 그 문서를 spec-interview의 출발점으로, 하네스 없음 쪽은 구현 요청의 본문으로 씁니다 |
| 같은 출발점 | 두 조건 모두 같은 기준 커밋에서 새 브랜치나 새 작업 트리로 시작합니다. 앞 실행의 결과물이 뒤 실행의 저장소에 남지 않게 합니다 |
| 같은 모델 | 모델, Claude Code 버전, 서브에이전트 허용 여부를 실행 4번 동안 바꾸지 않습니다 |
| 실행 기록 | 실행마다 기준 커밋, 브랜치, 세션 ID 목록, 모델, 시작과 끝 시각을 결과 문서에 적습니다 |

하네스 있음 쪽은 spec-interview부터 final-verify, review-gate까지 하네스 순서대로 진행합니다. 하네스 없음 쪽은 플랜 파일과 게이트 없이 구현하고, 사람이 평소대로 확인한 뒤 끝냅니다.

## 2. 지표

### 비용과 품질 신호

`cc-usage.sh` 의 그룹 비교로 쌍마다 한 번씩 잽니다. 하네스 있음 그룹에는 구현 세션뿐 아니라 spec-interview, plan-build, plan-verify, final-verify 세션도 모두 넣습니다. 이 세션들을 빼면 하네스 쪽 비용이 실제보다 작게 나옵니다.

```
cc-usage.sh --subagents --group-a <하네스 있음 세션들> --group-b <하네스 없음 세션들>
```

| 지표 | 출력 행 | 뜻 |
|---|---|---|
| 비용 | COST_USD | 명목 API 환산 비용. 절대액이 아니라 두 조건의 비율로 읽습니다 |
| 캐시 히트율 | HIT% | `cache_read / (cache_read + cache_create + input)` |
| 정정률 | CORR_RATE | 사람이 방향을 되돌린 프롬프트의 비율(정정 신호어 기준) |
| 재편집 | REDO | 같은 파일을 2회 이상 고친 파일 수 |
| 턴당 스텝 | STEPS/TURN | 사람 요청 1건당 API 호출 수 |

지표 정의와 한계는 `skills/harness-metrics/SKILL.md` 를 따릅니다. 정정률은 문자열 매칭이므로 수치가 튀면 해당 프롬프트 원문을 열어 확인합니다.

### 결함

결함은 두 가지를 따로 셉니다.

| 구분 | 무엇을 세는가 | 시점 |
|---|---|---|
| 게이트가 잡은 결함 | 하네스 있음 쪽에서 게이트가 지적하고 사람이 "맞음"으로 판정한 것 | 착수 전 또는 머지 전 |
| 나중에 드러난 결함 | 실행이 끝났다고 선언한 뒤 드러난 결함 | 머지 후 관찰 기간 |

게이트별로 잡는 시점이 다릅니다.

| 게이트 | 잡는 시점 | 원문이 남는 곳 |
|---|---|---|
| plan-verify | 착수 전 | 플랜 파일 끝의 `## 플랜 검증 결과` 절 (`.claude/harness/plan/<slug>.md`) |
| drift-watch | 구현 중, 머지 전 | `.claude/harness/report/drift-<slug>-<태스크ID>.md` |
| final-verify | 머지 전 | `.claude/harness/report/verify-<slug>-<YYYYMMDD>.md` |
| review-gate | 커밋과 머지 전 | 사용자 기록 `$(git rev-parse --git-dir)/review-gate/<kind>-<tree>.md`, 훅 거부 메시지(세션 로그) |

나중에 드러난 결함은 양쪽 조건 모두에서 셉니다. 하네스 없음 쪽에서 드러난 결함은 게이트가 없었을 때 새어 나간 것이고, 하네스 있음 쪽에서 드러난 결함은 게이트를 통과하고도 새어 나간 것입니다. 관찰 기간은 실행 4번에 같은 길이로 정하고(예: 머지 후 2주), 출처(수락 시험, 사람 리뷰, 운영 중 발견)를 함께 적습니다.

하네스 없음 쪽에서 사람이 구현 중에 직접 발견해 고친 문제는 세션 로그의 정정과 재편집에 이미 반영됩니다. 결함 표에는 끝났다고 선언한 뒤 드러난 것만 넣습니다.

## 3. 결함 판정 기록

### 원문 보존

게이트 출력은 고치거나 요약하지 않고 원문 그대로 보존합니다. `.claude/harness/report/` 의 파일은 같은 이름으로 다시 만들어질 수 있고, 플랜 검증 결과 절은 재실행 때 통째로 바뀌며, review-gate 기록은 git-dir 안에 있어 커밋되지 않습니다. 그래서 게이트가 끝날 때마다 사본을 따로 둡니다.

| 원본 | 사본 위치 |
|---|---|
| `.claude/harness/report/*.md` | `.claude/harness/metrics/<slug>/raw/<실행ID>/report/` |
| 플랜 파일(검증 결과 절 포함) | `.claude/harness/metrics/<slug>/raw/<실행ID>/plan/` |
| `$(git rev-parse --git-dir)/review-gate/*.md` | `.claude/harness/metrics/<slug>/raw/<실행ID>/review-gate/` |
| 세션 로그의 훅 거부 메시지 | `.claude/harness/metrics/<slug>/raw/<실행ID>/hook-deny.txt` (세션 JSONL에서 잘라 그대로 붙임) |

사본 폴더에는 파일마다 해시를 적은 `MANIFEST` 를 같이 둡니다. 판정을 마친 뒤 원문이 바뀌지 않았다는 것을 이 해시로 보입니다.

```
cd .claude/harness/metrics/<slug>/raw/<실행ID>
find . -type f ! -name MANIFEST | LC_ALL=C sort | xargs shasum -a 256 > MANIFEST
```

Linux에서는 `shasum -a 256` 대신 `sha256sum` 을 써도 같은 형식이 나옵니다.

### 판정 표

게이트 지적 하나마다 사람이 한 줄씩 판정합니다. 판정은 세 가지뿐입니다.

| 판정 | 뜻 |
|---|---|
| 맞음 | 실제 결함입니다. 그대로 두었다면 요구사항 위반, 버그, 운영 규칙 위반이 됐습니다 |
| 기각 | 결함이 아닙니다. 게이트가 틀렸거나, spec이 허용한 것이거나, 이미 처리된 것입니다 |
| 보류 | 지금 근거로는 정할 수 없습니다. 무엇을 확인하면 정해지는지 근거 칸에 적습니다 |

판정 근거는 한 줄로 적고, 확인한 위치(파일과 줄, 테스트 이름, spec 절)를 넣습니다. 비용 지표를 보기 전에 판정을 끝내 숫자가 판정에 끼어들지 않게 합니다.

예시 형식입니다. 아래 행은 형식을 보이기 위한 가상의 값입니다.

| ID | 실행 | 게이트 | 원문 위치 | 지적 요약 | 판정 | 판정 근거 (한 줄) |
|---|---|---|---|---|---|---|
| P1-01 | 쌍1-F1 | plan-verify | raw/r1/plan/order-cancel.md:142 | T3과 T4가 같은 파일을 고치는데 병렬로 표시됨 | 맞음 | 두 태스크 모두 `OrderService` 를 고침(플랜 T3, T4 파일 칸) |
| P1-02 | 쌍1-F1 | plan-verify | raw/r1/plan/order-cancel.md:150 | 환불 실패 시 재시도 정책 누락 | 기각 | spec 4.2절에서 재시도는 범위 밖으로 확정 |
| D1-01 | 쌍1-F1 | drift-watch | raw/r1/report/drift-order-cancel-T3.md:12 | 에러 코드가 spec과 다름 | 맞음 | spec 계약 표는 `ORDER_ALREADY_SHIPPED`, 구현은 `INVALID_STATE` |
| V1-01 | 쌍1-F1 | final-verify | raw/r1/report/verify-order-cancel-20261116.md:40 | 취소 API 동시 호출 시 이중 환불 가능 | 보류 | 동시성 테스트를 아직 돌리지 않음. 테스트 결과로 정함 |

판정 표 아래에 게이트별 집계를 붙입니다. 기각 수와 기각 비율도 빼지 않고 공개합니다. 게이트가 지적을 많이 내도 기각이 많으면 사람의 판정 시간만 늘린 것이기 때문입니다.

| 게이트 | 지적 수 | 맞음 | 기각 | 보류 | 기각 비율 |
|---|---|---|---|---|---|
| plan-verify | | | | | 기각 / 지적 수 |
| drift-watch | | | | | |
| final-verify | | | | | |
| review-gate | | | | | |
| 합계 | | | | | |

보류는 결함 수에 넣지 않고 따로 적습니다. 관찰 기간 안에 정해지면 판정을 바꾸고, 바꾼 날짜와 근거를 같은 행에 덧붙입니다. 처음 판정을 지우지 않습니다.

나중에 드러난 결함도 같은 형식의 표로 적되, 게이트 칸 대신 출처 칸(수락 시험, 사람 리뷰, 운영)을 씁니다.

## 4. 결과 표기 원칙

- 결과는 **사례 2건**으로 적습니다. 쌍 1과 쌍 2의 표를 따로 싣고, 두 쌍을 합친 평균이나 비율 하나로 요약하지 않습니다.
- 유의확률, 신뢰구간, "평균 몇 퍼센트 감소" 같은 통계 표현을 쓰지 않습니다. 표본이 2건이라 그런 수치가 뜻을 갖지 못합니다.
- 두 쌍이 같은 방향을 가리킬 때만 "이 두 사례에서는 하네스 쪽이 낮았다"처럼 사례에 묶어 씁니다. 방향이 갈리면 갈린 그대로 적고 판정하지 않습니다.
- 크기를 맞추지 못한 점, 관찰 기간, 판정자가 한 명이라는 점처럼 결과를 기울일 수 있는 조건을 결과 바로 옆에 적습니다.
- 게이트 원문 사본, `MANIFEST`, 판정 표, `cc-usage.sh` 실행 명령과 출력 원문을 결과 문서와 함께 둡니다. 다른 사람이 같은 원문으로 판정을 다시 해 볼 수 있어야 합니다.

결과 문서는 `.claude/harness/metrics/<slug>.md` 에 둡니다. `skills/harness-metrics/SKILL.md` 의 산출물 절이 정한 위치와 같습니다.
