# drift-watch

구현 중 이탈 감지. 태스크 하나가 끝난 그 시점에만 돈다.

## 발동 조건 (전부 만족할 때만)

1. `.claude/harness/plan/<slug>.md`의 태스크 하나가 방금 완료 처리됐다
2. 그 태스크가 소스 파일을 1개 이상 변경했다
3. `<repo>/.claude/harness/spec/` 또는 `plan/` 에 기준 문서가 있다

## 스킵 조건 (하나라도 걸리면 즉시 종료. 파일도 만들지 않는다)

| 조건 | 이유 |
|---|---|
| 변경이 문서, 주석, 포맷, import 정리뿐 | 판정 대상 3종 중 어느 것도 발생할 수 없다 |
| 변경 파일 3개 초과 | 태스크가 너무 크다. 쪼개라고 보고하고 종료 |
| 기준 문서(spec/plan)가 없다 | 요구사항 이탈을 판정할 기준선이 없다 |
| 같은 태스크에서 이미 1회 돌았다 | 태스크당 1회가 상한이다 |
| 구현이 전부 끝난 뒤다 | final-verify 담당 |

**상시로 돌지 않는다.** 파일 저장, 편집, 도구 호출마다 발동하는 것은 이 스킬의 사용법이 아니다. 상시 검증은 비용이 효과를 넘기 쉽고, 비싸지면 끄게 된다. 발동 빈도가 이 스킬의 생사다.

## 입력 수집 (범위를 넘기면 안 된다)

```bash
git diff --name-only HEAD   # 구현 스킬은 커밋하지 않으므로 작업트리 전체가 나온다
```

- 나온 목록에서 **이번 태스크 몫만** 남긴다. 앞선 태스크의 변경도 작업트리에 그대로 있으므로, 플랜 `## 실행 로그`의 그 태스크 줄에 적힌 변경 파일과 대조해 범위를 자른다
- **전체 diff, 전체 코드베이스를 읽지 않는다.** 위에서 나온 파일만 읽는다
- `spec/*.md`, `plan/*.md`는 전문을 읽지 않는다. **질문과 답 항목, 목표, 논골, 그 태스크의 행(건드리는 파일, 수정 금지)만** 읽는다
- 규칙은 프로젝트 `.claude/` 아래 규칙 문서나 규칙 스킬 중 해당하는 것만 읽는다. 전체 스킬 목록을 훑지 않는다
- 서브에이전트를 쓸 경우 1개까지. 전달 내용은 변경 파일 경로 + 기준 문서 발췌뿐이다

## 기계 대조 2종 (판정 전에 먼저 돌린다)

금지형 규칙은 지켜졌을 때 흔적이 남지 않는다. "막았다"와 "애초에 안 일어났다"를 구분할 수 없으니 효과를 잴 수 없다. 그래서 금지를 **감지 가능한 형태**로 바꿔 대조하고, 걸리면 기록이 남게 한다.

| 대조 | 방법 | 걸리면 |
|---|---|---|
| 수정 금지 침범 | 이번 태스크의 변경 파일 목록을 플랜 태스크 표의 `수정 금지` 경로나 glob과 대조 | `[요구사항 이탈]`로 보고. 확신도 높음. 근거는 플랜의 그 행 |
| 테스트 약화 | 이번 태스크가 바꾼 테스트 파일에서 assertion 수(`assert`, `expect`, `verify` 등 그 프로젝트의 단언 호출)를 `git diff HEAD` 기준 전후로 센다. 테스트가 삭제되거나 `@Disabled`, `skip` 같은 비활성 표시가 추가된 것도 센다 | 줄었으면 `[운영 규칙 위반]`으로 보고. 줄어든 이유가 플랜 태스크에 적혀 있으면 기각 |

두 대조는 걸리지 않아도 결과 줄 수만 남긴다(아래 산출물의 "이탈 없음" 줄). 발동 횟수가 쌓여야 이 규칙이 실제로 무엇을 잡는지 알 수 있다.

## 감지 대상 3종과 판정 기준

| 종류 | 판정 기준 |
|---|---|
| **할루시네이션** | 코드나 문서에서 근거를 특정할 수 없는 주장. 존재하지 않는 함수, 컬럼, 설정 옵션, API를 있다고 전제한 구현. 근거로 인용한 파일과 줄이 실재하지 않거나 그 주장을 뒷받침하지 않는 경우 포함 |
| **요구사항 이탈** | `.claude/harness/spec/*.md`의 질문과 답, 또는 `plan/*.md`의 목표와 논골과 충돌한다. 논골(하지 않기로 한 것)을 건드린 경우, 태스크의 `수정 금지` 경로를 건드린 경우도 이탈이다 |
| **운영 규칙 위반** | 프로젝트 `.claude/` 규칙 위반, 테스트 약화, 또는 운영 환경에 적용 불가한 것(로컬에서만 되는 경로, 하드코딩된 자격증명, 운영 데이터에 대해 되돌릴 수 없는 조작) |

## 판정 규율

기본값은 **기각**이다. 검증자도 모델이므로 검증자의 지적 자체가 할루시네이션일 수 있다.

- 소견이 지목한 **정확한 실패 입력 또는 경로를 코드에서 특정하지 못하면 기각**한다
- 판정마다 `파일:줄번호` 인용이 필수다. 인용을 못 붙이면 그 소견은 버린다
- 확신도(높음/중간/낮음)를 붙인다. 할루시네이션과 운영 규칙 위반은 **확신도 높음일 때만** 보고한다
- 요구사항 이탈은 충돌하는 spec/plan 문장을 그대로 인용해야 보고한다. 인용 없이 "의도와 다른 것 같다"는 보고하지 않는다
- 스타일, 취향, 개선 제안은 감지 대상이 아니다. 3종에 안 들어가면 침묵한다

## 산출물

**감지된 것이 하나도 없으면 파일을 만들지 않는다.** 다음 한 줄로 끝낸다.

```
drift-watch: 이탈 없음 (검사 파일 N개, 수정 금지 대조 N건, assertion 전후 N→N)
```

감지됐을 때만 `<repo>/.claude/harness/report/drift-<slug>-<태스크ID>.md`를 쓴다. 태스크당 1회만 돌므로 파일도 태스크당 하나다.

```markdown
# drift-watch: <slug> / <태스크ID> (YYYY-MM-DD HH:MM)

검사 파일: <경로 나열>
기준 문서: spec/<파일>.md, plan/<파일>.md
기계 대조: 수정 금지 N건 중 침범 M건 / assertion 전후 N→N

### [할루시네이션] <한 줄 제목> (확신도: 높음)

- 어긋난 지점: `경로/파일.kt:123`
- 무엇이 어긋났나: <근거를 특정할 수 없는 주장이 무엇이고 코드가 무엇을 전제하고 있는지>
- 반증 근거: <실제 코드나 문서에서 확인한 사실 + `경로:줄번호`>
- **질문**: <사용자에게 물을 것. 답에 따라 처리가 갈리는 지점을 묻는다>

### [요구사항 이탈] <한 줄 제목> (확신도: 높음)

- 어긋난 지점: `경로/파일.kt:45`
- 기준: spec/<파일>.md의 "<인용 문장>" 또는 plan 논골 "<인용 문장>" 또는 plan 태스크 행의 수정 금지 "<경로>"
- 충돌 내용: <구현이 기준의 무엇과 어떻게 충돌하는지>
- **질문**: <기준을 고칠 것인가, 구현을 고칠 것인가>

### [운영 규칙 위반] <한 줄 제목> (확신도: 높음)

- 어긋난 지점: `경로/파일.kt:78`
- 위반한 규칙: `.claude/<규칙파일>.md`의 "<인용>" 또는 테스트 약화(assertion N→M) 또는 운영 환경 제약
- **질문**: <사용자에게 물을 것>
```

## 정지 규칙

**AI가 스스로 고치지 않는다.** 보고서를 쓰고, 질문을 던지고, 멈춘다.

- 감지된 이탈을 자동 수정하지 않는다. 수정 코드를 미리 적용해 두지도 않는다
- 다음 태스크로 넘어가지 않는다. 사용자 답을 기다린다
- 보고서는 지우지 않는다. 이후 final-verify와 하네스 효과 측정(`harness-metrics`)의 입력이 된다
- 사용자가 반박하면 즉석에서 판정을 뒤집지 않는다. 인용한 `파일:줄번호`를 다시 확인하고, 근거가 반박 쪽이면 철회, 아니면 근거를 들어 유지, 확인 불가면 불명확으로 남긴다
