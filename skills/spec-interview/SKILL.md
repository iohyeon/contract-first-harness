# spec-interview: 요구사항 확정 인터뷰

## Purpose

사용자는 요구사항을 이미 파악해 왔다. AI가 할 일은 요구사항을 만드는 것이 아니라, 아직 결정되지 않은 지점을 집요하게 끄집어내 사용자의 결정으로 굳히는 것이다. 산출물인 spec 파일은 이후 final-verify가 요구사항 충족을 판정하는 기준선이 되고, plan-build가 이 파일을 읽고 이어받는다.

## 시작 전: 환경 실측

계약을 아무리 잘 정해도 실행 환경이 다르면 무효다. 이번 세션에서 `env-preflight`를 아직 돌리지 않았다면 먼저 돌리자고 제안한다. 런타임 버전, 저장소 루트, 포트 같은 환경 사실이 인터뷰의 전제가 되기 때문이다. 사용자가 생략을 택하면 spec의 `미결`에 "환경 실측 생략"을 남긴다.

## 사실과 결정

**사실(fact)은 직접 찾는다.** 파일시스템, 코드, 테이블 스키마, 기존 문서로 확인되는 것은 도구로 조회하고 `파일:줄번호`를 근거로 단다. 질문 목록에는 오르지 않는다. **결정(decision)은 사용자의 것이다.** 트레이드오프가 있고 환경이 답을 주지 않는 것만 질문한다. 이 구분이 질문 수를 결정한다.

## 인터뷰 방식

- **한 번에 하나씩 묻고 답을 기다린다.** 여러 질문을 한꺼번에 던지면 사용자가 답을 고르지 못한다
- **의존성 순서로 내려간다.** 결정 트리의 가지를 하나씩 타고, 앞의 답이 뒤의 질문을 바꾸게 둔다. 중요도 순서는 쓰지 않는다
- **각 질문에 AI의 추천 답을 근거와 함께 붙인다.** 사용자는 추천을 승인하거나 뒤집는 것만으로 답할 수 있다
- 질문이 10개를 넘어가면 요구사항이 아직 확정 단계가 아닐 수 있음을 알리고 범위 분할을 제안한다. 질문을 임의로 버리지 않는다
- 모든 결정이 굳으면 아래 `닫기 전 한 번 열기`를 거친 뒤 사용자에게 합의 도달을 확인받고 파일을 쓴다

## 계약을 먼저 확정한다

**계약(contract)** 은 여러 태스크가 공유하는 경계면이다. 계약이 흔들리면 구현은 직렬로 줄을 서고, 계약이 굳으면 그 뒤 태스크들이 서로 독립이 된다. 그래서 계약 질문을 인터뷰 앞쪽에 배치한다.

| 계약 종류 | 확정해야 하는 것 |
|---|---|
| 인터페이스 | 메서드 시그니처, 파라미터, 반환 타입 |
| DTO | 필드명, 타입, 필수 여부, 기본값 |
| 이벤트 | 토픽명, 페이로드 스키마, 발행 시점 |
| DB | 컬럼, 제약, 인덱스, 마이그레이션 순서 |
| 에러 | 에러 코드, HTTP 상태, 응답 바디 형태 |

확정된 계약은 spec 파일의 `## 확정된 계약` 절에 모은다. plan-build가 이 절을 읽고 병렬 태스크를 뽑는다.

## 질문 대상

| 유형 | 대상 | 이미 답이 있는 조건 |
|---|---|---|
| 엣지 케이스 | 경계값, null, 0, 최대치, 중복 요청, 동시 실행, 부분 실패 | 해당 입력의 결과가 요구사항에 적혀 있다 |
| 모호한 지점 | 두 가지로 읽히는 서술, 주체 없는 문장, 기준 시점 없는 조건 | 다른 사람이 읽어도 같은 판정이 나온다 |
| 운영 제약 | 기존 데이터, 하위 호환, 배포 순서, 권한, 외부 시스템 일정 | 기존 코드, 데이터, 일정과의 관계가 명시돼 있다 |
| 범위 경계 | 이번에 하지 않는 것 | 논골(non-goal, 하지 않을 것)이 요구사항에 적혀 있다 |

## 질문 형식

```markdown
#### Q3. 클라이언트가 보낸 주문 금액을 서버에서 재계산할 것인가

- 계약 질문: 예 (주문 요청 DTO / 에러 코드)
- 선행: Q1 확정 후
- 근거: `OrderService.java:132` 서버 검증 없음, 클라이언트 계산값을 그대로 저장
- 선택지
  - A: 클라이언트 값 신뢰. 구현 단순, 조작 가능
  - B: 서버 재계산 후 불일치 시 400. 상품 조회 1회 추가
- 추천: B. 금액 조작이 열려 있고 추가 비용은 요청당 조회 1회다
- 답: (사용자 답을 그대로 기록)
- 확정 문장: (참/거짓 판정 가능한 문장으로 변환)
```

## 확정 문장 기준

| 판정 | 문장 |
|---|---|
| 불가 | "수량을 적절히 제한한다", "성능에 문제가 없도록 한다" |
| 가능 | "PROD_QTY가 1 미만이거나 MAX_QTY 초과면 400을 반환한다" |
| 가능 | "PROD_QTY 미전달 요청은 1로 처리한다. 기존 클라이언트 하위 호환" |

## 닫기 전 한 번 열기

모든 질문이 답을 얻었다고 판단한 직후, 파일을 쓰기 전에 **한 번만** 열어 둔다. 사용자에게 아래 문장을 그대로 보여 준다.

```
추가로 확정할 계약이나 결정이 더 있으면 지금 한 번에 말해 달라.
spec을 닫고 병렬 구현이 시작되면 계약은 바꾸지 않는다.
```

- 같은 메시지에 AI가 스스로 찾은 **빠졌을 가능성이 있는 결정** 후보를 3개 이내로 붙인다. 계약 5종 중 이번 범위에서 비어 있는 칸, 엣지 케이스 표에서 답이 없는 칸이 후보다
- 새 질문이 나오면 위 질문 형식으로 처리하고, 끝나면 다시 이 단계를 거치지 않고 닫는다. 여는 것은 한 번이다. 반복하면 인터뷰가 끝나지 않는다
- 병렬 도중에 빠진 계약이 드러나면 모든 갈래를 멈춰야 한다. 닫기 전에 한 번 여는 비용이 그보다 싸다

시간 상한(예: "N분 안에 끝낸다")을 지시로 둘 수는 있으나 효과를 기대하지 않는다. 결정마다 근거가 붙어 있으면 멈출 이유가 없어 보여 라운드가 계속 늘어난다. 인터뷰를 끝내는 장치는 시간 상한이 아니라 이 단계다.

## 산출물

경로: `<repo>/.claude/harness/spec/<slug>.md`. 슬러그는 소문자와 하이픈만 쓴다(예: `order-cancel`). 디렉터리가 없으면 만든다. 계약과 확정 사항을 질문보다 앞에 둬서 이후 단계가 표만 읽고 기준선을 잡게 한다.

1. 제목과 작성일
2. **입력 요구사항** (사용자가 가져온 원문 그대로)
3. **확정된 계약** (표: 계약명 / 확정 형태 / 근거 질문 번호)
4. **확정 사항** (표: 번호 / 확정 문장 / 근거 질문 번호)
5. **질문과 답** (Q1부터 순서대로, 위 형식 그대로. 답과 미결 모두 원문 보존. 닫기 전 열기에서 나온 질문은 `(닫기 전 추가)`를 붙인다)
6. **미결** (표: 질문 번호 / 등급 / 사유 / 언제까지 필요한가). 판정 불가 문장도 여기로 내린다. 등급은 이 표에서만 쓰며 P0는 답이 없으면 착수 불가, P1은 결정 없이 완료 불가, P2는 범위 확인용
7. **범위 밖**

## Completion Criteria

- spec 파일이 `<repo>/.claude/harness/spec/<slug>.md`에 존재한다
- 모든 질문에 사용자의 답 또는 미결 사유가 붙어 있고, 미결 항목이 그대로 남아 있다
- 확정 사항 표의 모든 문장이 참/거짓 판정 가능하고 사용자의 답에서 나왔다
- 계약 5종 중 이번 범위에 해당하는 것이 `확정된 계약` 절에 적혀 있다
- 닫기 전 한 번 열기를 정확히 한 번 거쳤다
- P0 미결이 없다. 남아 있으면 착수 불가 상태임을 사용자에게 알렸다
