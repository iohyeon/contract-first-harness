# review-gate: 사용자 확인 기록 요청

## Purpose

모델이 만든 코드와 쿼리가 사람의 확인 없이 커밋되고 리뷰에 올라가는 일을 막는다. 확인했다는 증거는 사용자가 직접 남긴 기록 파일이고, 기록은 코드 내용(트리 해시)에 묶인다. 확인한 뒤 한 줄이라도 바뀌면 기록이 무효가 된다.

이 스킬은 사용자가 확인할 거리를 정확하게 내미는 일만 한다. 확인과 기록은 사용자가 한다.

## 구성 요소

| 요소 | 역할 |
|---|---|
| `hooks/review-gate.sh` | PreToolUse 훅. 기록이 없는 트리의 `git commit`, `git push`, `gh pr create`, `glab mr create` 를 거부한다. 모델의 기록 쓰기를 거부한다 |
| `bin/review-gate` | 사용자가 `!` 로 실행하는 CLI. `record`, `status`, `enable`, `disable` |
| 기록 파일 | `$(git rev-parse --git-dir)/review-gate/<kind>-<tree>.md`. git-dir 안이라 커밋되지 않는다 |

켜는 법은 저장소마다 `git config review-gate.enabled true` 이고, 사용자가 `! review-gate enable` 로 켜도 된다. 꺼진 저장소에서는 훅이 아무것도 막지 않는다.

## 기록 종류와 통과 조건

| kind | 언제 필요한가 | 사용자가 남기는 내용 |
|---|---|---|
| `code` | 항상 | 코드를 읽고 준 피드백 |
| `query` | 바뀐 파일 중 쿼리 패턴(`git config --get-all review-gate.query-pattern`, 기본 `*.sql`, `*Mapper.xml`)에 맞는 것이 있을 때 | 실제로 실행한 SQL과 결과 요약 |
| `loose` | 사용자가 느슨하게 가기로 정했을 때 | 느슨하게 가는 이유와 세 번의 문답 |

- commit 판정은 작업 트리 전체(추적 파일과 무시되지 않은 미추적 파일)의 트리로 한다. 그래서 작업 트리를 한 번 기록해 두면 그 상태를 여러 커밋으로 나눠도 다시 묻지 않는다.
- push, PR 생성 판정은 `HEAD^{tree}` 로 한다. 기록한 작업 트리를 전부 커밋했다면 같은 트리라 그대로 통과한다.
- loose 기록이 있으면 code, query 기록 없이 통과한다.

## 절차

### 1. 개발 단위가 끝났는지 본다

커밋마다 사용자를 부르지 않는다. 한 개발 단위(하나의 태스크, 하나의 기능, 리뷰에 함께 올릴 묶음)의 코드 변경을 모두 끝낸 뒤 한 번에 요청한다. 요청한 뒤에는 파일을 더 고치지 않는다. 고치면 트리가 바뀌어 사용자가 다시 기록해야 한다. 고칠 일이 생기면 먼저 고치고 나서 요청한다.

### 2. 현재 상태를 확인한다

```bash
review-gate status
```

`status` 는 읽기 전용이라 모델이 실행해도 된다. 출력에서 현재 tree, 바뀐 쿼리 파일, 필요한 기록과 있는 기록을 확인한다. `review-gate` 가 PATH 에 없으면 훅 거부 메시지에 나온 경로로 부른다.

### 3. 사용자에게 확인할 거리를 한 번에 제시한다

한 메시지에 아래를 모두 담는다.

**읽어야 할 코드 목록.** 바뀐 파일마다 경로와 바뀐 줄 범위, 무엇을 바꿨는지 한 줄, 사람이 특히 봐야 할 지점(트랜잭션 경계, 동시성, 예외 처리, 권한 검사 등 그 변경에서 틀리기 쉬운 곳)을 적는다. 바뀐 파일 목록은 `git diff --stat` 과 `git status --short` 로 만든다. 생성 파일이나 포맷만 바뀐 파일은 따로 묶어 표시한다.

**실제 실행 SQL.** 바뀐 쿼리 파일마다 사용자가 그대로 붙여 실행할 수 있는 SQL을 쓴다.

- 매퍼 XML 처럼 동적 SQL이면 바인딩 변수와 조건 분기를 펼쳐 실제로 나가는 문장을 쓴다. 분기가 여럿이면 분기마다 한 문장씩 쓴다.
- 바인딩 값은 테스트에서 쓴 값이나 현실적인 예시 값으로 채우고, 어떤 값을 넣었는지 밝힌다.
- 실행 계획을 함께 보도록 `EXPLAIN` 문장을 붙인다.
- 처음 쓰는 테이블, 새 조인, 인덱스를 타지 않을 수 있는 조건, 전체를 읽을 수 있는 쿼리는 따로 표시해 무엇을 봐 달라는지 적는다.
- 모델이 직접 실행한 결과가 있으면 함께 보여 주되, 그것으로 사용자 확인을 대신하지 않는다.

**기록 명령.** 사용자가 복사해 쓸 수 있게 적는다.

```text
! review-gate record code "<코드를 읽고 준 피드백>"
! review-gate record query "<실행한 SQL과 결과 요약>"
```

query 가 필요 없는 트리면 code 명령만 적는다.

### 4. 기다린다

사용자가 피드백을 주면 반영할지 묻는다. 반영해서 코드가 바뀌면 3번으로 돌아가 바뀐 부분만 다시 제시한다. 이때도 남은 수정을 모두 끝낸 뒤 한 번에 요청한다.

사용자가 기록을 남겼다고 하면 `review-gate status` 로 판정이 통과인지 확인한 뒤 커밋한다.

### 5. 느슨하게 가자는 요청

사용자가 "확인은 나중에", "빨리 가자" 처럼 느슨하게 가자고 하면 바로 따르지 않는다. 세 번 문답한다. 한 번에 한 질문씩 묻고 답을 받는다.

1. 왜 지금 확인 없이 가야 하는가(마감, 장애 대응, 실험 브랜치 등)
2. 확인하지 않은 코드와 쿼리가 틀렸을 때 어디까지 영향이 가는가
3. 언제, 어떻게 확인할 것인가

세 답을 받은 뒤 사용자가 기록하도록 명령을 내민다.

```text
! review-gate record loose "Q: 왜 지금인가 A: ... Q: 틀리면 영향은 A: ... Q: 언제 확인하나 A: ..."
```

느슨하게 가더라도 3번의 코드 목록과 실행 SQL은 그대로 제시한다. 사용자가 나중에 확인할 때 쓸 수 있게 하기 위해서다.

## 하지 않는 것

- 모델이 `review-gate record` 를 실행하지 않는다. 훅이 거부한다.
- 모델이 git-dir 아래 `review-gate/` 에 파일을 쓰거나 고치지 않는다. 훅이 거부한다.
- 변수, 다른 스크립트, 우회 경로로 기록 파일을 만들지 않는다. 훅은 명령 문자열만 보므로 기술적으로 다 막지 못한다. 막지 못하는 길이라도 쓰지 않는다.
- `git config review-gate.enabled` 를 끄거나 바꾸지 않는다. 끄는 것은 사용자가 정한다.
- 거부를 피하려고 커밋을 다른 명령 형태로 바꿔 실행하지 않는다.
- 커밋마다 따로 확인을 요청하지 않는다. 한 개발 단위에 한 번 묶는다.
