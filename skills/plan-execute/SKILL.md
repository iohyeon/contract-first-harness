# plan-execute

플랜 파일을 실행 명세로 삼아 구현한다. 이 스킬이 하는 일은 세 가지뿐이다.
태스크를 의존성대로 실행하고, 체크박스를 갱신하고, 플랜 밖으로 나가면 멈춘다.

새 규칙을 만드는 스킬이 아니라 **정지 조건을 거는 스킬**이다.

## 입력

- 플랜 파일: `.claude/harness/plan/<slug>.md` (인자로 경로가 오면 그것을 쓴다)
- 플랜이 없으면 실행하지 않는다. `plan-build`로 보낸다.

## 착수 절차

순서대로 한다. 하나라도 실패하면 멈추고 보고한다.

1. **승인 확인.** 플랜 파일 앞 20줄을 **Read 도구로** 읽고 승인 줄이 아래 정규식(ERE)에 매칭되는지 본다.
   ```
   ^\*\*승인\*\*:[[:space:]]*승인[[:space:]]*\(?[0-9]{4}-[0-9]{2}-[0-9]{2}
   ```
   `**승인**: 미승인`이거나 마커가 없으면 실행하지 않고 승인을 요청한다. **이 줄을 AI가 바꾸지 않는다.** Bash로 `grep`하지 않는다. 플랜 경로와 `승인`이 한 명령에 함께 들어가면 approval-gate 훅이 거부한다.
2. **환경 확인.** 오늘 날짜의 `.claude/harness/report/preflight-<slug>-<YYYYMMDD>.md`가 없거나, 있더라도 판정이 `❌ 착수 불가`면 `env-preflight`를 먼저 호출한다. 환경 실측은 요구사항보다 앞선다. 계약이 맞아도 런타임 버전, 포트, 저장소 루트가 다르면 구현은 무효다.
3. **실행 포인터 기록.** `.claude/harness/active-plan` 파일에 저장소 루트 기준 플랜 경로 한 줄을 Write 도구로 쓴다(예: `.claude/harness/plan/order-cancel.md`). 이미 다른 플랜을 가리키고 있으면 덮어쓰지 않고 멈춰서 묻는다. 다른 실행이 진행 중일 수 있다.

**approval-gate 훅이 이 포인터를 강제한다.** `active-plan`이 있고 가리키는 플랜이 승인 상태가 아니면 훅은 `.claude/harness/` 밖 파일에 대한 Edit, Write, MultiEdit와 Bash의 `codex exec`를 거부한다. 승인 후 플랜 본문이 바뀌어 `미승인`으로 되돌아가면 구현 편집이 그 자리에서 막힌다. 막혔을 때 포인터를 지워 우회하지 않는다. 멈추고 재승인을 요청한다.

## 실행 절차

1. **플랜 전문을 읽는다.** 목표, 논골, 전제, 태스크 목록(건드리는 파일과 수정 금지 포함), 의존성 그래프, 검증 명령을 확보한다.
2. **완료 상태를 먼저 확인한다.** `- [x]`는 건너뛴다. `- [!]`가 있으면 그 항목을 사람에게 먼저 확인한다.
3. **실행 가능한 태스크 집합을 뽑는다.** 선행 태스크가 전부 `[x]`인 것만 대상이다.
4. **아래 병렬 규칙과 Single Writer 규칙으로 분배한다.** 독립 태스크는 서브에이전트로 동시에, 의존이 걸린 것은 순서대로.
5. **태스크가 끝나면 플랜의 검증 명령을 실행하고 체크박스를 갱신한다.** 소스 파일이 바뀐 태스크는 이 시점에 `drift-watch`를 1회 돌린다.
6. 남은 태스크가 없을 때까지 3번으로 돌아간다.

태스크를 하다가 기존 동작을 설명하거나 원인을 단정해야 하면(전제가 맞는지 확인할 때, 검증 명령이 왜 실패하는지 찾을 때) 추측으로 넘어가지 않는다. 읽을 곳을 목록으로 뽑아 끝까지 읽고, 실측 전에 예측을 적어 두고 결과와 대조하고, 어긋나는 곳은 원인이 나올 때까지 따라간다. 가능하면 새 맥락의 검토자 에이전트에게 반박을 맡긴다. 그 태스크를 `[x]`로 바꾸는 것은 원인이 근거(`파일:줄번호` 또는 명령 출력)로 확인된 뒤에 한다. 분석 전용 스킬이 프로젝트에 있으면 그 절차를 쓴다.

## 정지 조건

플랜 밖의 상황을 만나면 아래 표로 판정한다. 판정이 갈리면 더 엄한 쪽(정지)을 택한다.

| 상황 | 판정 질문 | 행동 |
|---|---|---|
| **플랜의 전제가 틀렸다** | 플랜의 전제 섹션에 적힌 문장이 코드나 실행 결과와 어긋나는가 | **무조건 정지.** 반증 근거(파일:줄번호 또는 명령 출력)를 대고 보고한다. 전제 위에 세운 태스크를 계속 돌리지 않는다 |
| **논골에 해당한다** | 하려는 변경이 플랜의 논골 항목에 문자 그대로 걸리는가 | **무조건 정지.** 우회로를 찾지 않는다 |
| **수정 금지에 걸린다** | 하려는 변경이 이 태스크의 `수정 금지` 경로에 걸리는가 | **무조건 정지.** "필요해 보여서"는 사유가 아니다 |
| **새 파일** | 플랜의 영향도 섹션에 없는 파일을 새로 만드는가 | 정지하고 보고 |
| **새 의존성** | 패키지 매니페스트나 설정 파일에 항목이 추가되는가 | 정지하고 보고 |
| **새 설계 결정** | 선택지가 둘 이상이고, 어느 쪽을 골랐는지가 이후 태스크의 구현을 바꾸는가 | 정지하고 보고 |
| **태스크 범위 초과** | 이 태스크가 건드리는 파일이 3개를 넘는가 | 정지하고 보고. 플랜 단계에서 쪼개졌어야 하는 태스크다 |
| **검증 명령 실패** | 플랜의 검증 명령을 통과시키려면 위 항목 중 하나가 필요한가 | 정지하고 보고. 필요 없으면 고치고 계속한다 |
| **당연히 필요한 것** | (가) 플랜 작성 시점에 물었다면 사람이 "그건 당연히 해야지"라고 답할 것이고, (나) 위 항목 어디에도 걸리지 않는가 | 둘 다 참이면 **정지하지 않고 진행한다.** 하나라도 아니면 정지 |

"당연히 필요한 것"의 실제 예: import 추가, 오타 수정, 이미 있는 타입 시그니처에 맞추는 인자 수정,
기존 테스트 픽스처의 값 조정, 린터가 지적한 포맷 수정.
경계 사례: 함수를 하나 새로 만드는 것은 같은 파일 안이고 태스크 목표에 직결되면 진행,
파일이 새로 생기거나 다른 태스크가 그 함수를 쓰게 되면 정지다.

### 정지했을 때 보고 형식

```
정지: <태스크 ID>
사유: <위 표의 어느 행인가>
근거: <파일:줄번호 또는 명령 출력>
선택지: 1) ... 2) ...
```

선택지를 최소 2개 제시한다. 사람의 답을 받기 전에 플랜을 고치지 않는다.
플랜 수정이 필요하다는 결론이 나오면 `plan-build`로 넘긴다. 정지 중에는 `active-plan`을 지우지 않는다. 재개 지점이다.

## Single Writer: 파일마다 쓰는 사람은 1명

여러 작업자가 같은 파일을 쓰면 충돌보다 나쁜 일이 생긴다. 각자 자기 갈래가 끝난 시점의 이해로 공유 문서를 채우면서 **구현되지 않은 것을 구현됐다고 쓰고**, API 경로와 응답 필드가 문서마다 어긋나고, 같은 정책이 다른 표현으로 적힌다. 그래서 병렬 여부와 상관없이 기본 규칙으로 둔다.

- **모든 파일에는 소유자가 정확히 1명이다.** 태스크가 건드리는 파일은 그 태스크의 서브에이전트가 소유한다. 같은 시점에 두 작업자가 같은 파일의 소유자가 될 수 없다
- **공유 파일은 오케스트레이터(메인)만 쓴다.** README 같은 공유 문서, 공통 계약 파일(C 구간 산출물), 공통 설정, 플랜 파일(체크박스와 실행 로그 포함)이 여기에 든다. 서브에이전트는 이 파일들을 직접 고치지 않는다
- 서브에이전트가 공유 파일 변경이 필요하다고 판단하면 쓰지 않고 아래 형식으로 **보고**한다. 메인이 모아서 한 번에 반영하고, 반영 전 실제 구현과 대조한다

```
- 필요한 변경:
- 필요한 이유:
- 변경하지 않으면 막히는 작업:
```

- 문서의 "구현됨" 서술은 메인이 검증 명령 결과를 확인한 뒤에만 쓴다

## 병렬 실행 규칙

### 병렬로 돌릴 수 있는 것

플랜의 병렬 표시를 그대로 따르되, 실행 직전에 아래를 다시 확인한다.

- **같은 파일을 건드리는 태스크는 병렬로 돌리지 않는다.** 플랜에 병렬로 표시돼 있어도 마찬가지다.
  플랜의 태스크 표에서 파일 목록이 겹치거나, 한 태스크의 파일이 병렬 이웃의 `수정 금지`에 걸리면 순차로 내린다. 발견한 사실을 보고에 남긴다.
- 한 태스크는 서브에이전트 하나가 소유한다. 소유 경계는 파일 단위로 자른다.
- 서브에이전트에게는 플랜의 목표, 논골, 해당 태스크, 그 태스크의 **담당 파일과 수정 금지 목록**, 검증 명령, Single Writer 보고 형식만 준다.
  플랜 전문과 다른 태스크의 내용을 주지 않는다. 담당만 주고 금지를 빼면 "필요해 보여서" 남의 영역을 건드린다.

### 격리 수준은 선택 변수다

격리 자체가 목적이 아니라 **소유권 명시가 목적**이다. 격리 수준은 작업 길이에 따라 고른다.

| 작업 길이 | 적정 격리 | 이유 |
|---|---|---|
| 며칠 단위 | 브랜치 또는 git worktree | 머지 비용이 전체 대비 작고, 갈래별 되돌리기가 쉽다 |
| 시간 단위 | 동일 작업 트리 + 파일 소유권 + Single Writer | 머지가 곧 병목이 된다. 격리 도구가 그 환경에서 도는지 검증하는 비용도 든다 |

어느 쪽이든 Single Writer와 수정 금지는 그대로 적용한다. worktree를 쓰기로 했으면 그 환경에서 worktree 생성과 머지가 실제로 도는지 `env-preflight` 단계에서 먼저 확인한다. 선택한 격리 수준은 실행 로그 첫 줄에 남긴다.

### 배리어가 필요한 조건

아래 셋 중 하나라도 참이면 배리어를 둔다. 전부 거짓이면 배리어 없이 병렬로 흘려보낸다.

| 의존 | 판정 질문 | 배리어 필요 여부 |
|---|---|---|
| 데이터 의존 | 다음 태스크의 입력이 앞 태스크의 산출물인가 | 항목별로 독립이면 배리어 없이 파이프라인. **전체를 모아야 판단이 서는 경우에만 배리어** |
| 합의 의존 | 두 태스크의 산출물이 같은 용어, 같은 경계, 같은 규칙을 공유해야 하는가 | 공유 대상을 앞 태스크에서 먼저 고정하고 그 결과를 뒤 태스크에 입력으로 준다. 고정이 안 돼 있으면 **정지하고 보고** (플랜 단계에서 고정됐어야 한다) |
| 인지 의존 | 산출물의 소비자가 사람이고, 전부 읽어야 의미가 생기는가 | **병렬 대상에서 제외하고 순차로 돌린다** |

배리어 판별의 실무 기준 하나: 다음 단계에서 "다른 태스크들의 결과"를 언급해야 하면 배리어가 필요하다.
언급하지 않아도 되면 결과를 모으려고 배리어를 두지 않는다.

구현 태스크는 대체로 합의 의존이 지배적이므로 병렬 폭을 넓게 잡지 않는다.
검증 성격의 태스크는 서로의 결론이 섞이지 않는 편이 낫기 때문에 병렬이 유리하다.

### 통합은 하나씩 붙이고 그 자리에서 기동한다

병렬 갈래를 전부 만든 뒤 한꺼번에 합치지 않는다. 한 갈래를 붙일 때마다 플랜의 기동 명령(애플리케이션 컨텍스트 기동 등)을 그 자리에서 돌린다. 단위 테스트는 컨텍스트를 띄우지 않아 빈 생성 경로나 설정 누락을 못 잡는다. 여러 갈래가 섞인 뒤 기동이 깨지면 원인을 찾는 비용이 갈래 수만큼 커진다.

## 체크박스 갱신

컴팩트 복구 지점이다. 태스크 하나가 끝날 때마다 즉시 갱신한다. 몰아서 하지 않는다. 플랜 파일은 메인만 갱신한다(Single Writer).

- 완료: `- [ ]` → `- [x]`
- 정지: `- [ ]` → `- [!]`
- 플랜 하단 `## 실행 로그` 섹션에 **태스크당 한 줄**만 추가한다.
  형식: `- T3 완료 2026-07-28 / 변경: src/a.ts, src/b.ts / 검증: pnpm test 통과`
  정지한 경우: `- T4 정지 2026-07-28 / 사유: 새 의존성 / 근거: package.json`
- 실행 로그를 제외한 플랜 본문(목표, 논골, 전제, 태스크 문구, 수정 금지, 의존성 그래프)과 승인 줄은 **고치지 않는다.**
  플랜 본문이 틀렸다고 판단되면 그것 자체가 정지 조건이다.
- 로그 한 줄이 두 줄 이상으로 길어지면 태스크가 너무 크다는 신호다. 보고에 남긴다.

## 세션 재개

컴팩트되었거나 세션이 새로 시작됐다면 플랜 파일과 `.claude/harness/active-plan`만 다시 읽는다.
`[x]`까지가 완료된 범위이고, 실행 로그의 마지막 줄이 마지막 상태다. 승인 줄도 다시 확인한다. 그 사이 사람이 `미승인`으로 되돌렸을 수 있다.
대화 기록을 복원하려 하지 않는다. 플랜 파일에 없는 진행 상황은 없는 것으로 간주하고,
불확실하면 해당 태스크의 검증 명령을 다시 실행해 현재 상태를 확인한다.

## 완료 시

- 모든 태스크가 `[x]`가 되면 플랜의 검증 방법 섹션 전체(기동 명령 포함)를 한 번 더 실행한다.
- `.claude/harness/active-plan`을 지운다(`rm .claude/harness/active-plan`). 지우지 않으면 다음 작업에서 이 플랜의 승인 상태가 계속 편집을 가른다.
- 보고: 완료 태스크 수, 정지 이력, 병렬로 돌린 태스크와 순차로 내린 태스크, 선택한 격리 수준, 서브에이전트가 보고한 공유 파일 변경과 반영 여부, 남은 미해결 항목.
- 최종 전체 검증은 이 스킬이 하지 않는다. `final-verify`로 넘긴다.
- 커밋과 푸시는 하지 않는다. 사람이 지시할 때만 한다.
