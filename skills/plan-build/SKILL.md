# plan-build

플랜은 설계서가 아니라 **실행 계약**이다. 설계의 깊이는 spec 문서가 갖고, 플랜은 그 설계에서 뽑아낸 실행 단위와 의존 관계만 갖는다.

## 이 스킬이 푸는 문제

촘촘하게 설계할수록 태스크가 서로 얽혀 보이고 결국 직렬로 흐른다. 이때 원인을 촘촘함으로 돌리면 해법이 "덜 촘촘하게"가 되어 설계 품질을 버리게 된다. 잘못된 트레이드오프다.

병렬을 막는 것은 촘촘함이 아니라 **계약이 늦게 확정되는 것**이다. 두 태스크가 얽혀 보이는 이유는 둘 사이의 인터페이스가 아직 안 정해졌기 때문이다. 계약이 확정되면 두 태스크는 서로를 몰라도 된다.

사람 팀에서는 이 빈칸을 실행 중 대화로 메운다. **서브에이전트는 서로 대화하지 못한다.** 각자 그럴듯하지만 서로 다른 값으로 빈칸을 메우고, 그 발산은 통합 시점에야 드러난다. 그래서 AI 오케스트레이션에서 계약 확정은 품질 규율이 아니라 **병렬 성립의 전제 조건**이다.

## 상한과 그 근거

| 항목 | 상한 | 근거 |
|---|---|---|
| 플랜 본문 | 150줄 | **재읽기 비용.** 플랜은 세션마다 다시 읽히고 컴팩트 복구 지점으로 쓰인다. 작성 비용이 아니라 반복 로드 비용이 문제다 |
| spec 문서 | **상한 없음** | 한 번 쓰고 선택적으로 참조한다. 촘촘할수록 좋다 |
| 태스크 하나가 건드리는 파일 | 3개 | 넘으면 그 태스크를 쪼갠다 |
| 태스크 개수 | 12개 | 넘으면 플랜을 둘로 나눈다 |

플랜이 150줄을 넘는다면 설계가 과한 게 아니라 **설계 내용이 플랜에 새어 들어온 것**이다. 그 부분을 spec 문서로 옮기고 플랜에서는 링크한다.

## 입력

`.claude/harness/spec/<slug>.md` 를 읽는다. 특히 `## 확정된 계약` 절이 이 스킬의 핵심 입력이다. 그 절이 병렬 태스크를 가르는 칼이다.

spec 파일이 없으면 플랜에 그 사실을 명시한다. 나중에 final-verify 3층이 기준선 부재로 판정 불가가 된다.

`env-preflight` 결과(`.claude/harness/report/preflight-<slug>-<YYYYMMDD>.md`)가 있으면 전제 표와 검증 방법을 쓸 때 참고한다. 실측된 런타임 버전, 빌드 명령, 포트를 그대로 옮긴다.

## 산출물

`.claude/harness/plan/<slug>.md`. 슬러그는 spec 파일과 같은 이름을 쓴다.

## 세 구간 구조

태스크를 나열하지 말고 세 구간으로 배치한다.

```
[C] 계약 고정   직렬. 혼자. 촘촘하게.
     인터페이스 시그니처, DTO 필드, 이벤트 스키마, DB 스키마, 에러 코드
        │  계약이 확정되면 아래가 서로 독립이 된다
        ▼
[I] 구현        병렬. 각 구현체는 서로를 모른다
        │
        ▼
[V] 통합, 검증  배리어. 모아야 판단이 서는 것
```

`## 확정된 계약`이 spec에서 이미 확정됐다면 C 구간은 비어도 된다. 비어 있지 않다면 **C를 먼저 끝내기 전에는 I를 시작하지 않는다.**

## 필수 섹션 9개

순서를 지킨다. 비어 있으면 "없음"이라고 쓰되 섹션을 생략하지 않는다.

**1. 승인** 플랜 제목 바로 아래, **파일 앞 20줄 안에** 아래 한 줄을 그대로 넣는다. 훅과 다른 스킬은 앞 20줄만 읽고 승인 여부를 판정한다. **이 줄이 플랜 전체에서 유일한 승인 마커다.**

```
**승인**: 미승인
```

사람만 이 줄을 `**승인**: 승인 YYYY-MM-DD <메모>` 로 바꾼다. 하위 호환으로 `**승인**: 승인 (YYYY-MM-DD, 메모)` 도 승인으로 인정된다. 승인 판정 정규식(ERE)은 아래와 같다.

```
^\*\*승인\*\*:[[:space:]]*승인[[:space:]]*\(?[0-9]{4}-[0-9]{2}-[0-9]{2}
```

AI가 이 줄을 승인 상태로 바꾸는 편집은 approval-gate 훅이 거부한다. plan-build는 `미승인`으로만 쓴다.

**2. 메타** 작성일, spec 파일 경로, 관련 이슈, 기준 커밋 SHA(`git rev-parse HEAD`). 기준 커밋은 drift-watch와 final-verify가 변경 범위를 자르는 기준이므로 빼면 안 된다.

**3. Context** 지금 어떤 문제가 있고 왜 지금 하는가. 이미 결정된 것. 5줄 이내.

**4. 목표** 무엇이 되면 끝인가. 판정 가능한 문장으로.

**5. 논골** 하지 않을 것(non-goal). 이름을 `논골`로 고정한다. 각 항목은 세 가지를 함께 적는다.

```
- 재고 관리 시스템 구축: 이번 범위 아님. 별건 T3-3으로 이관
- Value Object 검증 로직 변경: 도메인 불변식 보호이므로 현행 유지
```

무엇을 안 하는가 / 왜 안 하는가 / 어디로 갔는가(있으면).

**6. 전제** 플랜을 이렇게 짠 근거가 된, 참이라고 믿는 사실. 미확인 질문이 아니라 선언이다.

| # | 전제 | 근거 | 틀렸을 때 영향 |
|---|---|---|---|
| A1 | 주문 금액 검증은 서버에서만 한다 | spec Q2 답변 | 클라이언트 계산 로직 재설계 |

근거 칸에는 파일 경로, spec 질문 번호, 확인한 코드 위치를 적는다. 근거를 못 대면 전제가 아니라 미확인 항목이므로 spec으로 돌려보낸다. plan-verify가 각 행에 반증을 시도하므로 **반증 가능한 문장**이어야 한다.

**7. 태스크와 의존성**

| ID | 구간 | 태스크 | 건드리는 파일 | 수정 금지 | 선행 | 병렬 |
|---|---|---|---|---|---|---|
| C1 | C | 결제 취소 포트 시그니처 확정 | `PaymentClient.java` | 구현체 전부 | - | 단독 |
| I1 | I | PG 취소 실호출 구현 | `PaymentClientImpl.java` | `PaymentClient.java`(계약), `order/` | C1 | 가능 |
| I2 | I | 실패 시 DLQ 적재 | `CompensationDlq.java`, `DlqService.java` | `PaymentClient.java`(계약), `PaymentClientImpl.java` | C1 | 가능 |
| V1 | V | 중복 취소 방지 통합 테스트 | `PaymentE2ETest.java` | `src/main/` 전체 | I1, I2 | 배리어 |

`선행` 칸이 의존성 그래프다. plan-verify와 plan-execute가 이 칸을 그래프로 읽으므로 별도 그래프를 따로 그리지 않는다.

**`수정 금지` 칸은 비우지 않는다.** 담당 파일만 주면 작업자는 "필요해 보여서" 남의 영역을 건드린다. 금지 목록을 함께 줄 때 실제로 지켜진다. 채우는 기준은 셋이다.

- 계약 파일: C 구간에서 고정한 인터페이스, DTO, 스키마. I 구간의 모든 태스크에 금지로 적는다
- 병렬 이웃의 담당 파일: 같은 시점에 도는 다른 태스크가 건드리는 파일과 경로
- 공유 파일: README, 공통 설정, 플랜 자신. 이 파일들은 오케스트레이터(메인) 소유이며 태스크는 직접 쓰지 않고 필요한 변경을 보고한다(plan-execute의 Single Writer 규칙)

금지는 경로나 glob으로 쓴다. "건드리지 마라" 같은 서술은 쓰지 않는다. 경로로 적혀 있어야 drift-watch가 변경 파일 목록과 대조해 위반을 **기록**할 수 있다. 감지할 수 없는 금지는 지켜졌는지도 알 수 없다.

체크박스는 표 아래 별도로 둔다. plan-execute와 codex-handoff가 이 줄을 갱신하고, 플랜 맨 아래 빈 `## 실행 로그` 섹션에 한 줄씩 추가한다. 그 섹션은 plan-build가 비워 둔 채로 만들어 둔다.

- [ ] C1 결제 취소 포트 시그니처 확정
- [ ] I1 PG 취소 실호출 구현
- [ ] I2 실패 시 DLQ 적재
- [ ] V1 중복 취소 방지 통합 테스트

**8. 영향도** 변경될 파일과 영향받는 도메인. 태스크 표와 겹치면 도메인만 적는다.

**9. 검증 방법** 실행 가능한 명령으로 쓴다. 서술로 쓰지 않는다. 빌드와 테스트뿐 아니라 **기동 명령**도 함께 적는다. final-verify의 기동 층이 이 명령을 쓴다.

```bash
./gradlew test --tests '*Order*'      # 테스트
./gradlew bootRun                       # 기동 (컨텍스트가 뜨는가)
curl -fsS localhost:8080/health         # 실제 HTTP 응답
```

명령으로 확인할 수 없는 것은 무엇을 눈으로 볼지 한 줄로 적는다.

## 병렬 판정을 양방향으로 한다

한쪽만 보면 절반을 놓친다.

| 방향 | 질문 | 놓치면 |
|---|---|---|
| 겹치는데 병렬로 표시 | 두 태스크가 같은 파일을 건드리는가, 앞의 결과값을 입력으로 쓰는가 | 충돌하고 재작업한다 |
| **독립인데 직렬로 표시** | 이 두 태스크가 반드시 순서를 지켜야 할 근거를 댈 수 있는가 | **병렬 기회를 통째로 버린다** |

두 번째를 기본으로 의심하라. **근거를 못 대면 병렬이다.** 순서를 지켜야 한다는 쪽에 입증 책임을 둔다.

| 조건 | 판정 |
|---|---|
| 건드리는 파일이 겹친다 | 병렬 불가 |
| 한 태스크의 건드리는 파일이 다른 병렬 태스크의 수정 금지에 걸린다 | 표가 모순이다. 둘 중 하나를 고친다 |
| 앞 태스크의 결과값을 입력으로 쓴다 | 병렬 불가 (데이터 의존) |
| 앞 태스크들의 결과를 **모아야** 판단이 선다 | 배리어 |
| 위 어디에도 안 걸린다 | **병렬** |

배리어와 단순 선행의 차이는 "전체를 모아야 판단이 서는가"로 가른다. 다음 단계가 다른 태스크들의 결과를 언급해야 한다면 배리어다.

## 적지 않을 것

구현 코드, 메서드 본문, SQL 전문, 클래스 설계 상세, 다이어그램, 일정 추정, AS-IS/TO-BE 서술. 앞의 넷은 spec 문서로, 일정은 플랜의 역할이 아니고, AS-IS/TO-BE는 작업 후 기록이다.

## 절차

1. spec의 `## 확정된 계약` 절을 읽는다. 없으면 그 사실을 기록하고 C 구간을 직접 만든다
2. 논골부터 쓴다. 범위를 먼저 닫아야 태스크가 늘어나지 않는다
3. 전제를 쓴다. 근거를 못 대는 항목은 spec으로 돌려보낸다
4. 태스크를 C / I / V 세 구간에 배치한다
5. 태스크를 나눈다. 파일 3개를 넘으면 그 자리에서 쪼갠다
6. 태스크마다 `수정 금지`를 채운다. 계약 파일, 병렬 이웃의 파일, 공유 파일 순으로 확인한다
7. 병렬을 양방향으로 판정한다. 직렬로 묶은 것마다 근거를 댈 수 있는지 확인한다
8. 검증 명령을 쓴다. 테스트 명령과 기동 명령을 모두 쓴다
9. 줄 수를 센다. 150줄을 넘으면 설계 내용이 새어 들어온 것이므로 spec으로 옮긴다
10. 승인 줄이 앞 20줄 안에 `미승인`으로 있는지 Read로 확인하고 plan-verify로 넘긴다. **스스로 통과 판정하지 않는다**

## Completion Criteria

- 필수 섹션 9개가 모두 있다
- 승인 줄이 파일 앞 20줄 안에 `미승인` 상태로 정확히 한 줄 있다
- 메타에 기준 커밋 SHA가 있고, 맨 아래에 빈 `## 실행 로그` 섹션이 있다
- 전제 표의 각 행에 근거가 있다
- 모든 태스크가 C / I / V 중 하나에 속하고 병렬 판정이 붙어 있다
- 모든 태스크의 `수정 금지` 칸이 경로나 glob으로 채워져 있다
- 직렬로 묶인 태스크마다 그래야 하는 근거가 있다
- 검증 방법이 실행 가능한 명령이고 기동 명령을 포함한다
- 본문이 150줄 이내다
- 사람이 이 파일만 읽고 승인하거나 반려할 수 있다
