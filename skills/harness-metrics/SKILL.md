# harness-metrics

**측정 없이 하네스를 바꾸지 않는다.** 플랜 문서는 "효과 대비 비싸다"는 체감만으로 넣거나 걷어내기 쉽다. 그 체감이 맞는지 숫자로 확인하는 것이 이 스킬의 존재 이유다.

## 스크립트

`scripts/cc-usage.sh` (이 스킬 폴더 기준). 플러그인으로 설치했다면 `${CLAUDE_PLUGIN_ROOT}/skills/harness-metrics/scripts/cc-usage.sh` 다. 의존성은 bash(3.2 이상), jq, awk 다.

로그 루트는 `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/projects` 이고 `--root <dir>` 로 바꿀 수 있다.

| 호출 | 의미 |
|---|---|
| `cc-usage.sh` | 현재 디렉터리 프로젝트의 모든 세션 |
| `cc-usage.sh /path/to/project` | 특정 프로젝트 경로 |
| `cc-usage.sh <슬러그>` | `<로그 루트>/<슬러그>` 직접 지정 |
| `cc-usage.sh <세션>.jsonl` | 세션 파일 1건 |
| `--subagents` | 서브에이전트 토큰까지 합산. **비교할 때는 항상 켠다** |
| `--quality` | 정정, 거부, 중단, 에러툴, 재편집, 스텝/턴 프록시 표 추가 |
| `--json` | 세션당 JSON 한 줄. 모델별 분리 집계 등 후처리용 |
| `--all` | API 호출 0건인 빈 세션도 표시 |
| `--root <dir>` | 로그 루트 지정. `CLAUDE_CONFIG_DIR` 보다 우선 |
| `--group-a id1,id2 --group-b id3,id4` | 세션 두 그룹을 합산해 나란히 비교한다. ID는 앞부분만 줘도 하나로 정해지면 되고, `.jsonl` 경로도 받는다 |
| `-h` | 사용법 |

기본 호출은 `cc-usage.sh --subagents --quality <경로>` 다.

## 왜 --subagents 가 필수인가

서브에이전트 토큰은 메인 세션 JSONL에 합산되지 않는다. `<세션UUID>/subagents/agent-*.jsonl` 에 분리 기록된다. 병렬 위임이 많은 작업 방식에서 이 플래그를 빼면 비용을 크게 과소 보고한다.

`~/.claude.json` 의 `lastTotal*` 필드는 쓰지 않는다. 마지막 세션 1건만 담고 비정상 종료 시 0이 된다.

## A/B 비교 절차

전체 절차와 결함 판정 기록 형식은 [docs/measurement.md](../../docs/measurement.md) 에 있다. 여기에는 이 스크립트로 재는 부분만 적는다.

1. **크기가 비슷한 기능 2개(F1, F2)를 고른다.** 건드리는 파일 수, 새로 정하는 계약 수, 외부 연동 유무가 비슷해야 한다. 맞추지 못했으면 그 차이를 산출물에 적는다.
2. **쌍 2개를 순서 교차로 실행한다.** A는 하네스 있음(spec-interview, plan-build, plan-verify, plan-execute와 게이트), B는 하네스 없음이다. 기능 난이도와 학습 효과가 한 조건에 몰리지 않게 쌍 2에서 조건을 뒤집는다.

   | 쌍 | 1번째 실행 | 2번째 실행 |
   |---|---|---|
   | 쌍 1 | F1, 하네스 있음(A) | F2, 하네스 없음(B) |
   | 쌍 2 | F1, 하네스 없음(B) | F2, 하네스 있음(A) |

3. **매 실행은 새 세션에서, 같은 spec 문서만 입력으로 시작한다.** 같은 기준 커밋에서 새 브랜치나 작업 트리로 시작하고, 모델과 Claude Code 버전을 바꾸지 않는다.
4. 각 실행이 끝나면 **그 실행의 세션만** 지정해 측정한다. 프로젝트 전체를 재면 다른 작업이 섞인다. 세션 ID는 로그 루트 아래 `<슬러그>/<세션UUID>.jsonl` 파일 이름이다.
   ```
   cc-usage.sh --subagents --quality <로그 루트>/<슬러그>/<세션UUID>.jsonl
   ```
5. 쌍마다 그룹 비교를 한 번씩 돌린다. A에는 구현 세션뿐 아니라 spec, 플랜 작성, 플랜 검증, 최종 검증 세션도 넣는다. 이 세션들을 빼면 비교가 기울어진다.
   ```
   cc-usage.sh --subagents --group-a <spec>,<플랜 작성>,<플랜 검증>,<구현>,<최종 검증> --group-b <구현>
   ```
6. 아래 표를 **쌍마다 하나씩** 채운다. 그룹 비교 출력의 행 이름을 출처 칸에 적었다. 두 쌍을 합친 표는 만들지 않는다.

| 지표 | 하네스 있음(A) | 하네스 없음(B) | 출처 |
|---|---|---|---|
| 턴수 | | | TURNS |
| 출력 토큰 | | | OUT |
| 캐시 히트율 | | | HIT% |
| 비용(USD) | | | COST_USD |
| 정정률 | | | CORR_RATE (정정 / TURNS) |
| 재편집 파일 수 | | | REDO (재편집) |
| 스텝/턴 | | | STEPS/TURN (스텝/턴) |

그룹 비교의 `B/A` 열은 B를 A로 나눈 값이다. 판정 기준표의 비율은 A 기준이므로 거꾸로 읽지 않게 주의한다.

게이트(plan-verify, drift-watch, final-verify, review-gate)가 잡은 결함과 하네스 없음 쪽에서 나중에 드러난 결함은 이 스크립트가 세지 못한다. 게이트 원문을 고치지 않고 보존하고, 사람이 지적마다 맞음, 기각, 보류로 판정한 표를 따로 만든다. 형식은 docs/measurement.md 의 "결함 판정 기록" 절을 따른다.

## 지표를 어떻게 읽는가

| 지표 | 읽는 법 |
|---|---|
| 턴수 | 사람이 개입한 횟수. 줄면 자율성이 올라간 것이고, 늘면 방향을 자주 잡아줬다는 뜻이다 |
| 출력 토큰 | 생성량. 비용의 주된 축이다. 같은 결과를 더 적은 출력으로 냈으면 이득 |
| 캐시 히트율 | `cache_read / (cache_read + cache_create + input)`. 이미 90% 이상이면 캐시 쪽 개선 여지는 없다고 본다 |
| 비용 | 명목 환산값. 절대액이 아니라 A와 B의 **비율**로만 읽는다 |
| 정정률 | 유저 프롬프트 중 정정, 부정 신호어("아니", "다시", "잘못", "revert", "instead" 등) 포함 비율. **방향을 되돌린 비율**이다. 이 스킬에서 가장 중요한 품질 프록시 |
| 재편집 | 같은 파일을 2회 이상 Edit/Write 한 파일 수. **한 번에 못 맞춘 파일 수**. 메인 세션 파일 기준이다 |
| 스텝/턴 | 유저 요구 1건당 API 호출 수. 높으면 요구가 모호했거나 과잉 탐색을 했다는 신호다. 다만 요구가 굵어서 긴 자율 실행이 일어난 경우에도 높아지므로 턴수와 함께 본다 |
| 에러툴 | is_error tool_result 수. 환경 탐색 실패나 잘못된 가정 |

프록시는 전부 대리 신호다. 인과가 아니다. 정정 신호어는 문자열 매칭이라 "다시 한 번 정리해줘" 같은 무해한 문장도 잡는다. 수치가 튀면 원문을 직접 확인하고 판정에 반영한다.

## 판정 기준

| 조건 | 판정 |
|---|---|
| 정정률 A <= B의 1/2 **이고** 비용 A <= B x 1.1 | 플랜이 값을 한다. 유지 |
| 정정률 A <= B의 1/2 **이지만** 비용 A > B x 1.3 | 조건부. 되돌리기 비용이 큰 작업(마이그레이션, 외부 연동)에만 쓴다 |
| 정정률이 절반까지 안 떨어지고 비용만 증가 | 플랜이 값을 못 한다. 걷어낸다 |
| 재편집이 절반 이하로 줄고 출력 토큰이 늘지 않음 | 플랜이 값을 한다는 보조 근거 |
| 어느 쪽이든 차이가 20% 미만 | **판정 불가.** 표본 부족이다. 작업 쌍을 더 모은다 |

비교 쌍 1건으로 결론을 내지 않는다. 최소 2쌍이 같은 방향을 가리켜야 판정한다. 결과는 통계가 아니라 사례 2건으로 적는다. 쌍마다 결과를 따로 싣고, 두 쌍이 갈리면 갈린 그대로 적는다.

## 한계 (산출물에 반드시 적는다)

- **실제 청구액이 아니다.** 구독 플랜 사용자의 명목 API 환산값이다.
- **단가는 추정 단가이며 env로 덮어쓸 것.** 기본값은 공개 가격표의 입력/출력 단가에 캐시 쓰기 1.25배, 캐시 읽기 0.1배를 적용한 값이다. 가격은 바뀌고 모델마다 캐시 배수가 다를 수 있으니, 측정 시점의 가격표를 확인해 `HM_PRICE_INPUT`, `HM_PRICE_OUTPUT`, `HM_PRICE_CACHE_WRITE`, `HM_PRICE_CACHE_READ` (USD per 1M tokens)로 덮어쓴다. env는 모든 모델에 같은 값으로 적용된다. 적용된 기본 단가는 출력 마지막 줄에 나온다.
- 스크립트의 모델 분류는 haiku, sonnet 5, sonnet 4.x, 그 밖(opus 계열 단가)이다. 표에 없는 모델은 opus 계열 단가로 계산하므로 더 비싼 모델은 과소, 더 싼 모델은 과대 추정된다.
- 캐시 쓰기 TTL 구분이 반영되지 않는다. 5분 TTL 단가로만 계산하므로 1시간 캐시를 많이 쓰면 과소 추정된다.
- 세션에 여러 모델이 섞이면(서브에이전트 포함) 호출 수가 가장 많은 지배 모델 단가를 일괄 적용한다. 혼합이 감지되면 출력 마지막 줄에 표시된다. 정확한 분리는 `--json` 후처리가 필요하다.
- 품질 프록시는 문자열과 구조 신호이고 결과물의 옳고 그름을 모른다.

## 산출물

`<repo>/.claude/harness/metrics/<슬러그>.md` 에 남긴다. 슬러그는 비교한 작업을 알아볼 수 있는 이름이다.

담을 것: 실행한 명령 원문, 출력 표 원문, 적용한 단가, A/B 비교표, 판정과 그 근거, 위 한계. 해석은 사실에 근거해서만 쓰고 추측은 추측이라고 표시한다.
