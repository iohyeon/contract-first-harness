# Plan Verify

잡아야 하는 것은 코드 결함이 아니라 **잘못된 가정**이다. 구현 도중 "이걸 놓쳤네, 롤백해야겠네"가 되는 시점을 플랜 단계로 당긴다.

## 인자 파싱

`$ARGUMENTS`가 플랜 파일 경로면 그 파일을, 없으면 `<repo>/.claude/harness/plan/` 의 최근 수정 파일을 검증한다. 같은 슬러그의 `<repo>/.claude/harness/spec/<slug>.md` 가 있으면 계약 축과 누락 축의 기준선으로 읽고, 없으면 두 축을 건너뛴다.

## 핵심 원칙

1. **기본 판정은 기각이다.** 반증이 근거를 특정하지 못하면 버린다. 반증이 기각되면 플랜 항목은 통과다.
2. **판정마다 근거 인용 필수.** 파일:줄번호, 또는 spec 문서의 해당 질문과 답. 근거 없는 "위험해 보임"은 금지.
3. **확신도 게이트.** 모든 반증은 (a) 구체적 실패 시나리오("어떤 상황에서 플랜의 무엇이 깨지는가")와 (b) 확신도(높음/중간/낮음)를 포함한다. 하나라도 못 적으면 버리거나 `question:`으로 강등한다. **높음**일 때만 플랜 수정을 요구한다.
4. **플랜이 단일 진실 소스다.** 검증 결과는 플랜 파일 안에 쓴다. 별도 보고서 파일을 만들지 않는다.

### 판정 라벨: 대상은 플랜 항목이 아니라 **에이전트가 시도한 반증**이다

| 라벨 | 의미 | 플랜에 대한 처리 |
|------|------|------------------|
| ❌ 기각 | 반증 실패. 근거를 특정하지 못했거나 플랜이 이미 다루고 있음 | **통과.** 그대로 진행 |
| ✅ 확인 | 반증 성공. 코드나 문서에서 근거를 특정함 | **수정 필요.** 승인 전에 고친다 |
| 🔍 불확실 | 근거가 양쪽으로 갈림 | 사람이 판단. 단정하지 않는다 |

## Step 1: 플랜 파싱

플랜 파일을 Read로 읽고 5개 축의 검증 대상을 뽑아 `/tmp/plan-verify-<slug>-axis<N>.md` 로 저장한다.

| 축 | 뽑는 것 |
|------|------|
| 1 전제 | 전제 표의 각 행 (전제 문장 + 근거) |
| 2 태스크 | 태스크 목록 전체 + 목표 1줄 + 논골 |
| 3 병렬 표시 | 태스크 **전부** + 각 태스크의 건드리는 파일과 수정 금지 + 의존성 그래프 (병렬 표시된 것만 뽑지 않는다) |
| 4 계약 | spec의 `## 확정된 계약` 표 전체 + 플랜의 태스크 제목과 건드리는 파일 |
| 5 누락 | spec 파일의 질문과 답 목록 + 플랜의 태스크 제목 목록 |

전제 표나 의존성 그래프가 아예 없으면 그 축은 검증 불가다. **플랜이 `plan-build` 필수 섹션을 안 갖췄다고 보고하고 멈춘다.** 없는 것을 지어내서 검증하지 않는다. `수정 금지` 칸이 비어 있는 태스크도 같은 이유로 보고한다.

## Step 2: 축별 적대적 에이전트 (5개 병렬)

5개 축은 서로 독립이므로 배리어가 없다. 에이전트 5개를 동시에 띄우고, 각 에이전트에게 담당 축 파일 경로만 준다. 공통 지시:

```
"한국어로 답하라."
"각 항목 판정: ❌ 기각(반증 실패, 플랜 통과) / ✅ 확인(반증 성공, 수정 필요) / 🔍 불확실."
"판정마다 근거를 파일:줄번호 또는 문서 인용으로 1줄 명시하라. 근거를 못 대면 ❌ 기각이다."
"각 ✅ 확인에는 실패 시나리오와 확신도(높음/중간/낮음)를 붙여라. 못 붙이면 보고하지 마라."
```

**축 1. 전제**
```
"각 전제에 대해 그 전제가 사실이 아님을 증명하라. 코드나 문서에서 반증을 찾지 못하면
 기본 판정은 통과(❌ 기각)다. Grep과 Read로 실제 코드를 확인하라. 추측으로 반증하지 마라."
```

**축 2. 태스크**
```
"각 태스크에 대해 그 태스크가 목표에 기여하지 않음을 증명하라. 목표와의 연결을 설명할 수
 있으면 기각이다. 논골에 적힌 것을 하고 있는 태스크가 있으면 그것도 보고하라."
```

**축 3. 병렬 표시 (양방향)** 방향 A는 거짓 병렬, 방향 B는 놓친 병렬이다. 둘 다 보고하게 한다.

```
"방향 A: 병렬 ✅ 로 표시된 두 태스크가 같은 파일을 건드리거나 한쪽 산출물을 다른 쪽이
 입력으로 쓴다는 것을 증명하라. Grep으로 실제 파일 경로를 확인하고 겹치는 파일을 특정하면
 ✅ 확인이고 이 쌍은 배리어가 필요하다. 같은 모듈이라는 이유만으로는 근거가 아니다.
 한 태스크의 건드리는 파일이 같은 시점 병렬 태스크의 수정 금지에 걸리면 그것도 ✅ 확인이다."

"방향 B: 직렬로 묶인 두 태스크가 반드시 순서를 지켜야 함을 증명하라. 겹치는 파일 경로나
 데이터 의존(앞 태스크의 산출물을 뒤가 읽는다)을 특정하지 못하면 ✅ 확인이고, 이 쌍은
 병렬로 표시돼야 한다. '순서대로 하는 게 자연스럽다'는 근거가 아니다."
```

방향 B가 이 축의 무게 중심이다. 병렬 표시가 0건인 플랜은 그 자체로 방향 B의 검사 대상이다. 느린 것은 되돌릴 수 있으므로 방향 A의 확신도 기준을 방향 B보다 낮게 잡는다.

**축 4. 계약** 계약이 확정돼야 뒤따르는 구현 태스크가 병렬로 갈라진다. 계약이 흐리면 플랜의 병렬 표시는 전부 거짓이 된다.

```
"이 계약이 확정되지 않았음을 증명하라. 셋을 본다.
 (1) 시그니처, 필드, 에러 코드가 참/거짓 판정 가능한가. '적절한 응답을 반환한다' 같은 모호한
     서술이면 ✅ 확인, 타입과 필수 여부와 값이 특정되면 기각이다.
 (2) 이 계약이 두 태스크의 경계를 실제로 자르는가. 계약만 보고 양쪽을 따로 구현할 수 없으면
     ✅ 확인이고, 그 두 태스크는 병렬로 표시되면 안 된다.
 (3) 계약에 있는데 만드는 태스크가 없거나, 태스크가 계약과 다른 필드나 타입을 전제하면 ✅ 확인.
 판정마다 spec의 계약 행과 플랜의 태스크 번호를 함께 인용하라."
```

**축 5. 누락**
```
"spec의 질문과 답 중 플랜의 어느 태스크에도 반영되지 않은 것을 찾아라. 반영된 태스크를
 지목할 수 있으면 기각이다. 논골에 명시적으로 제외된 항목은 누락이 아니다."
```

## Step 3: 합성 (메인이 5개 축 결과를 모아 판단한다)

| 에이전트 판정 | 처리 |
|------|------|
| ✅ 확인 + 확신도 높음 | **확정.** 플랜 수정 대상 |
| ✅ 확인 + 확신도 중간 또는 낮음 | 메인이 근거를 직접 확인 후 유지 또는 강등 |
| 🔍 불확실 | 사람 판단 항목으로 남긴다. 메인이 결론 내지 않는다 |
| ❌ 기각 | 출력하지 않는다. 개수만 집계 |

축 간 중복은 제거한다. 축 4가 계약 미확정을 잡은 태스크 쌍은 축 3 방향 B의 대상에서 뺀다. 계약이 안 굳은 상태에서 병렬로 올리라는 요구는 서로 모순이다.

## Step 4: 플랜 파일에 결과 추가

플랜 파일 맨 끝에 `## 플랜 검증 결과` 섹션을 Edit로 **추가**한다. 기존 내용은 지우지 않고, 재실행 시에는 이 섹션만 통째로 교체한다.

```markdown
## 플랜 검증 결과

검증 일시: YYYY-MM-DD / 반증 시도 N건 중 확정 M건

### 수정 필요 (승인 전)
| # | 축 | 대상 | 무엇이 깨지는가 | 근거 | 확신도 |
|---|---|---|---|---|---|
| 1 | 전제 | A2 | <실패 시나리오 1줄> | `경로:줄` | 높음 |

### 사람 판단 필요 (🔍)
| # | 축 | 대상 | 갈리는 지점 |
|---|---|---|---|

### 통과
전제 N/N, 태스크 N/N, 계약 N/N, 병렬 쌍 N/N(A방향 N, B방향 N), spec 반영 N/N.

### 판정: ✅ 승인 요청 / 🔄 플랜 수정 필요
```

수정 필요와 불확실이 모두 0건일 때만 `✅ 승인 요청`이다. **승인 마커는 이 섹션에 쓰지 않는다.** 플랜 상단의 승인 줄이 유일한 마커이고, 여기서는 `미승인` 상태인지 확인만 한다.

## 승인 마커

판정 줄은 AI의 의견이고 승인 마커는 사람의 결정이다. 승인이 대화에만 남으면 세션이 바뀔 때 사라지므로 파일에 남긴다.

마커는 플랜 파일 **앞 20줄 안에 한 줄만** 존재한다. plan-build가 제목 바로 아래 만든 그 줄이며, 아래 형태 중 하나다. 두 줄 이상이면 어느 줄이 진실인지 갈리므로 그 자체가 보고 대상이다.

```
**승인**: 미승인
**승인**: 승인 YYYY-MM-DD <자유 메모>
**승인**: 승인 (YYYY-MM-DD, 메모)        ← 하위 호환
```

승인 판정 정규식(ERE):

```
^\*\*승인\*\*:[[:space:]]*승인[[:space:]]*\(?[0-9]{4}-[0-9]{2}-[0-9]{2}
```

이 정규식에 매칭되는 줄이 앞 20줄 안에 있을 때만 착수 가능이다. 매칭이 안 되면 `미승인`이든 마커가 없든 착수 금지로 취급한다.

- **승인 줄은 Read 도구로 읽는다.** Bash 명령에 `.claude/harness/plan/` 경로와 `승인`이 함께 들어가면 approval-gate 훅이 마커 조작으로 보고 거부한다. `grep`이나 `sed`로 확인하지 않는다
- plan-verify는 판정이 `✅ 승인 요청`이어도 그 줄을 **항상 `미승인`으로 둔다**
- **AI는 이 줄을 승인 상태로 바꾸지 않는다.** 검증 통과, 재실행, 시간 경과, 다른 스킬의 필요, 사용자의 "승인해 줘" 발화 어느 것도 사유가 되지 않는다. 미승인을 승인으로 바꾸는 Edit, Write, MultiEdit는 approval-gate 훅이 거부한다. 사람이 에디터에서 직접 바꾼다
- 승인 후 플랜 본문(태스크, 의존성, 계약 전제, 수정 금지)이 바뀌면 `미승인`으로 되돌리고 바뀐 부분만 재검증한다. 되돌리는 편집은 훅이 막지 않는다. 체크박스와 실행 로그 갱신은 되돌림 사유가 아니다
- `plan-execute`와 `codex-handoff`는 착수 전 이 줄을 읽고, 승인이 아니면 멈추고 승인을 요청한다

## 사람 승인 게이트

검증 결과를 출력한 뒤 **멈춘다.** 이 하네스에서 사람이 개입하는 지점은 여기 하나뿐이다.

- 플랜을 대신 고치지 않는다. 수정 제안까지만 하고 승인을 기다린다
- 사용자가 수정을 지시하면 고치고, 고친 항목만 재검증한다(전체 재실행 금지)
- 사람이 마커를 승인으로 바꾸면 `plan-execute` 또는 `codex-handoff` 로 넘어간다

## 반박 대응 (Anti-Sycophancy)

사용자가 판정에 반박하면 **대화 모델이 즉석에서 재판단하지 않는다.** 반박 압박 하에서는 근거 없이 굴복하기 쉽다. 에이전트 1개로 중립 블라인드 판정한다.

- **전달**: 해당 항목의 발췌 **하나만** + 두 가설. "가설 A: <원래 판정>", "가설 B: <반박 내용>". **누가 어느 쪽 주장인지 밝히지 않는다**(self-blinding)
- **지시**: "코드나 문서 인용만으로 A/B 중 무엇이 맞는지 판정하라. 근거를 못 대면 '불명확'. 어느 쪽이 사용자 주장인지 추측하거나 만족시키려 하지 마라."
- **반영**: 근거가 B 손을 들면 판정을 철회한다. A 손을 들면 인용을 들어 유지한다. "불명확"이면 🔍 로 남긴다
- **토큰**: 발췌 1개 + 2가설만 전달하고, 반박이 들어왔을 때만 실행한다

## 주의사항

- 출력은 한국어. 에이전트에게는 축별 발췌 파일만 주고 플랜 전문은 주지 않는다
- 플랜의 구현 상세를 요구하지 않는다. 플랜은 합의문이지 설계서가 아니다
- 코드 품질과 버그는 이 스킬의 대상이 아니다. 그건 `final-verify`와 커밋 전 리뷰(`review-gate`)가 본다
