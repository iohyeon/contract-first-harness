# ecommerce-design: 이커머스 설계 게이트

이커머스 설계 요청을 받으면 **바로 산출물을 만들지 않는다.** 이 도메인의 사고는 대부분 "무엇을 만드는가"가 아니라 "어느 전제를 골랐는가"에서 갈리고, 전제를 안 정한 채 만든 설계는 나중에 정산이 안 맞는 형태로 되돌아온다.

이 스킬은 전제를 먼저 확정시키고, 확정된 전제에 따라 분기 규칙을 적용한다.

---

## 언제 쓰나 (TRIGGER, 해당 시에만)

도메인 게이트는 **선택 단계**다. 대상이 커머스 도메인일 때만 쓰고, 아니면 건너뛴다. 앞서 `requirements-analysis`가 돌았다면 `.claude/harness/domain/<slug>.md` 를 먼저 읽고, 거기 적힌 확정된 결정과 겹치는 게이트는 다시 묻지 않는다.

- "주문 도메인 설계해줘 / 재고 어떻게 관리하지 / 결제 붙이려는데 / 정산 로직 어떻게"
- 이커머스 기획서, 요구사항 문서를 받아 정리하거나 검토할 때
- 커머스 관련 ERD, 상태기계, API 설계
- 키워드: 커머스, 쇼핑몰, 마켓플레이스, 셀러, 입점, 장바구니, 주문서, 재고, 오버셀, 부분취소, 환불, 정산, 수수료, 풀필먼트

---

## 동작 순서

### 0단계. 게이트 스코핑 (질문하기 전에 한다)

**게이트 10개를 전부 묻지 않는다.** 요청에 실제로 걸리는 것만 고른다.

| 요청 유형 | 필요한 게이트 |
|---|---|
| 장바구니 | G4 |
| 상품, 카탈로그, 옵션 | G1, G4 |
| 재고 | G1, G2, G3 |
| 주문 생성, 주문서 | G1, G3, G4, G5, G6, G8 |
| 주문 상태, 주문 조회 | G8, G9 |
| 결제 연동 | G5, G6, G9, G10 |
| 취소, 환불, 부분취소 | G5, G7, G9 |
| 쿠폰, 할인, 프로모션 | G7 |
| 정산, 수수료 | G1, G7, G10 |
| 전체 도메인 설계, 기획 검토 | 전부 |

표에 없는 요청은 가장 가까운 행을 쓰고, 판단이 애매하면 G1(판매 형태)만 먼저 확인한다. G1은 거의 모든 분기의 상위에 있다.

### 1단계. 게이트 통과

`references/00-gates.md`에서 **스코핑된 항목만** 읽고 답을 확보한다.

순서는 다음과 같다.

1. **사용자가 이미 말한 것**은 넘어간다
2. **코드베이스나 문서에서 확인 가능한 것은 직접 조회한다.** 셀러 엔티티 존재 여부(G1), 재고 차감 위치(G2, G3), 주문 스냅샷 컬럼 유무(G4), 멱등키 컬럼(G6) 같은 항목은 사용자에게 묻기 전에 코드를 본다. 확인한 내용은 "코드에서 확인함"으로 표시하고 사용자에게 검토받는다
3. **결정이 필요한 것만 묻는다.** 한 번에 하나씩, 추천안을 붙여서
4. 사용자가 "알아서 해달라"고 하면 추천안으로 잠정 확정하고 **그 전제를 산출물 맨 앞에 명시**한다

### 게이트와 산출물 의존 관계

게이트를 못 채웠을 때 무엇을 만들 수 없는지의 매핑이다.

| 못 채운 게이트 | 만들 수 없는 것 |
|---|---|
| G1 판매 형태 | 정산 설계, 주문 분할 설계, 상품 등록 흐름 |
| G2 재고 정본 | 오버셀 방어 설계, 재고 동기화 설계 |
| G3 차감 시점 | 주문 생성 트랜잭션 경계, 선점 스키마 |
| G4 스냅샷 경계 | 주문 스키마, 환불 금액 산정 |
| G5 실행 순서 | 주문과 결제 연동 흐름, 보상 설계 |
| G6 멱등키 | 결제 API 스펙, 재시도 정책 |
| G7 금액 규칙 | 부분취소 금액 산정, 정산 금액 산정 |
| G8 주문 분할 | 주문 스키마, 배송 스키마 |
| G9 상태 전이 | 상태기계, 클레임 흐름 |
| G10 대사 | 실패 설계의 최종 방어선 |

해당 게이트가 비어 있으면 그 산출물은 만들지 않고, **무엇이 막혀 있는지 명시한다.** 나머지 산출물은 정상적으로 만든다.

### 2단계. 도메인 카드 적용

관련된 카드만 읽는다. 전부 읽지 않는다. **한 요청이 여러 카드에 걸리면 모두 읽는다.**

| 주제 | 참조 |
|---|---|
| 상품 모델, SPU/SKU, 옵션, 카탈로그, 리스팅, 재고, 오버셀, 차감 시점 | `references/01-catalog-inventory.md` |
| 장바구니, 주문서, 주문 분할, 스냅샷, 멱등, 주문 상태 | `references/02-order.md` |
| PG, 승인과 매입, 취소와 환불, 복합결제, 웹훅 | `references/03-payment.md` |
| 금액, 안분, 단수 처리, 되돌리는 값, 상태 전이 원칙 | `references/99-crosscutting.md` |
| 클레임 정책, 풀필먼트, 배송, 정산, 대사 | `references/90-uncovered.md` |

**겹치는 요청의 우선순위.** 검증된 카드를 먼저 적용하고, 미검증 영역은 그 뒤에 고려사항으로 덧붙인다.

| 요청 | 순서 |
|---|---|
| 부분취소, 환불 금액 | 03-payment(수단별 순서, 잔액) + 99(안분) 먼저 → 90(귀책, 회수 정책) 나중 |
| 반품 시 재고 복구 | 01(재고 3수량) 먼저 → 90(검수 후 재입고 판정) 나중 |
| 정산 금액 산정 | 99(안분, 부담 주체) 먼저 → 90(마감, 원장) 나중 |

미검증 영역에서 나온 내용은 확정 규칙이 아니라 **결정이 필요한 항목**으로 제시한다.

### 3단계. 산출물 생성

게이트 답과 카드 규칙을 적용해 만든다. 산출물 형식은 아래 "산출물 규격"을 따르고, 저장 위치는 "저장 위치"를 따른다.

외부 시스템(PG, 메시징, 서드파티 API) 호출이 걸리면 이어서 `analyze-external-integration`을 거친다(해당 시에만).

## 강제 규칙

### 1. 전제를 명시하지 않은 설계를 내지 않는다

모든 산출물 첫머리에 확정된 전제를 적는다.

```
전제
- 판매 형태: 3P 중개 (셀러 직배송)
- 재고 정본: 셀러 시스템, 플랫폼은 복제본
- 재고 차감: 주문 생성 시 선점, 출고 시 실물 차감
- 취소 순서: 재고 선점 → 결제 승인
```

### 2. 1P와 3P를 구분하지 않은 답을 내지 않는다

같은 질문이라도 판매 형태에 따라 답이 갈리는 항목이 많다. 형태를 모르면 먼저 묻는다. 양쪽 다 필요하면 나란히 제시한다.

### 3. 금액이 나오면 검산 두 줄을 붙인다

- 나눈 할인의 합 = 원래 할인액
- 항목별 실부담의 합 = 결제액

### 4. 없는 것을 지어내지 않는다

`references/90-uncovered.md`에 해당하는 영역(클레임, 풀필먼트, 정산)은 검증된 판단 규칙이 아직 없다. 그 영역을 다룰 때는 **일반적인 고려사항 수준임을 명시**하고, 확정 규칙처럼 서술하지 않는다.

법령, 특정 회사의 계약 형태, PG 스펙은 원문 확인 없이 단정하지 않는다.

### 5. em dash 금지

긴 줄표를 쓰지 않는다. 쉼표, 마침표, 괄호로 끊는다.

## 산출물 규격

요청 종류에 따라 아래 중 필요한 것만 만든다.

| 요청 | 산출물 |
|---|---|
| 요구사항 정리 | 전제 + 확정 항목 + 미결 항목 + 판정 가능한 문장으로 쓴 요구사항 목록 |
| 도메인 설계 | 전제 + 애그리거트 경계 + 경계를 넘는 것과 넘지 않는 것 + ERD |
| 상태 설계 | 상태 목록 + 허용 전이표 + 역방향을 표현하는 새 상태 + 전이 트리거 |
| 실패 설계 | 실패 시나리오별 감지 지점, 보상 동작, 최종 방어선(대사) |
| 기획 검토 | 게이트 항목 중 기획서에 답이 없는 것 목록 + 그로 인해 나중에 터질 지점 |

상태 설계에는 반드시 역방향(취소, 반품)을 포함한다. 정방향만 있는 상태기계는 미완성으로 본다.

### 저장 위치

산출물은 대상 저장소 `<repo>/.claude/harness/domain/<slug>.md` 에 남긴다. 세 도메인 게이트가 같은 파일을 공유한다.

- 슬러그는 뒤따를 spec 파일과 같은 이름을 쓴다
- 파일이 있으면 이 스킬의 절만 붙인다. 없으면 `# <slug> 도메인 게이트`, 작성일, 입력 요구사항 원문을 머리에 두고 새로 만든다
- 이 스킬의 절은 `## 커머스 게이트`다. 이미 있으면 갱신 날짜를 적고 고친다
- 절 첫머리에 강제 규칙 1의 전제 블록과 스코핑한 게이트 목록을 두고, 위 표의 산출물을 그 아래에 둔다. 막힌 산출물은 무엇이 막혔는지 적는다
- 절 끝에 `### 확정된 결정`을 번호 목록으로 둔다. 사용자가 답했거나 코드에서 확인하고 검토받은 게이트만 넣고, 게이트 번호(G1 등)와 근거를 붙인다. "알아서 해달라"로 잠정 확정한 것은 `(잠정, 추천안)`을 붙인다
- 그 아래 `### 열린 질문`을 번호 목록으로 둔다. 답이 없는 게이트, 미검증 영역에서 나온 결정 필요 항목을 적는다. `spec-interview`가 이 목록을 인터뷰 질문 후보로 쓴다

## 근거

저자의 이커머스 도메인 학습 노트에서 증류했다. 카탈로그와 재고, 주문, 결제는 노트 기반이고 클레임, 풀필먼트, 정산은 개괄 수준이다.
