# final-verify: 최종 전체 검증

한 작업의 구현이 끝났을 때 종료해도 되는지 판정한다. 판정 결과는 보고서로 남고 지우지 않는다.

발동 조건은 `.claude/harness/plan/<slug>.md` 의 태스크 체크박스가 전부 채워졌을 때, 또는 사용자가 최종 검증을 명시적으로 요청했을 때다. 플랜 파일이 없어도 실행할 수 있으나 3층 판정이 제한된다.

---

## Step 0. 기준선 수집

층별 기준선을 먼저 확보한다. 기준선이 없는 층은 추측으로 판정하지 않는다.

| 층 | 검증 대상 | 기준선 | 없을 때 |
|---|---|---|---|
| 1층 규칙 | 코딩 컨벤션, 네이밍, 공통 모듈과 유틸리티 사용, 에러 코드 정책 | 프로젝트 `.claude/` 규칙 문서나 규칙 스킬, `CLAUDE.md` | 코드베이스 내 다수 패턴을 근거로만 지적 |
| 2층 아키텍처 | 레이어 구조, 의존성 방향, 임의 클래스와 모듈 추가, 공통 구조 우회 | 프로젝트 아키텍처 문서, 기존 모듈 구조 | 기존 동일 계층 코드를 기준선으로 사용 |
| 3층 요구사항 | 기능 충족, 누락된 예외 조건, 엣지 케이스, 최초 범위 준수 | `.claude/harness/spec/<slug>.md` + `plan/<slug>.md` | **🔍 판정 불가로 명시하고 넘어간다** |
| 4층 기동 | 애플리케이션이 실제로 뜨는가, 실제 요청에 응답하는가, 깨끗한 사본에서도 뜨는가 | 플랜 `검증 방법`의 기동 명령, `env-preflight` 리포트, README의 실행 방법 | 사용자에게 기동 명령을 묻는다. 추측한 명령으로 통과 처리하지 않는다 |

**3층에 spec 파일이 없으면 요구사항 검증은 하지 않는다.** 없는 요구사항을 상상해서 채점하면 채점 자체가 할루시네이션이 된다. 보고서에 "기준선 부재로 판정 불가"라고 쓰고, 조치 항목으로 `spec-interview` 실행을 제안한다.

변경 범위도 여기서 확정한다. 기준 커밋은 플랜 메타 섹션의 기준 커밋 SHA이고, 없으면 사용자에게 묻는다.

```bash
git diff --name-only <기준커밋> > /tmp/fv-files.txt
git diff <기준커밋> > /tmp/fv-diff.txt
```

`..HEAD`를 붙이지 않는다. plan-execute와 codex-handoff는 커밋하지 않으므로 변경이 작업트리에만 있고, `<기준커밋>..HEAD`로 자르면 diff가 비어 나온다.

## Step 1. 3층 병렬 검증 + 기동 층 실행 (배리어 없음)

1~3층은 서로 독립이다. 한 층의 결과가 다른 층의 입력이 아니므로 동시에 띄운다. 4층은 명령 실행이므로 에이전트에게 맡기지 않고 메인이 그동안 직접 돌린다.

```
메인 ─ 기준선 수집 + 4층 기동 실행 + 합성 + 최종 판정
├─ Agent L1 ── 1층 규칙      ← .claude/ 규칙 + 변경 파일 목록
├─ Agent L2 ── 2층 아키텍처   ← 아키텍처 문서 + 변경 파일 목록
└─ Agent L3 ── 3층 요구사항   ← spec.md + plan.md + 변경 파일 목록
        ↓ (여기가 유일한 배리어)
   Agent F ─── 적대적 필터
```

세 에이전트에게 공통으로 지시할 것.

1. 담당 층의 기준선 파일 경로와 `/tmp/fv-files.txt` 경로. 전체 diff 본문을 프롬프트에 붙이지 않는다
2. "기준선 문서에 근거 문장이 없으면 지적하지 마라. 근거는 `문서:줄번호` 또는 코드 `파일:줄번호`로 인용하라"
3. "각 소견에 상태 마커를 붙여라: ✅ 충족 / ⚠️ 부분 충족 / ❌ 미충족 / 🔍 판정 불가"
4. "각 ❌, ⚠️ 소견에 구체적 실패 시나리오(어떤 입력과 상황에서 무엇이 깨지는가)를 1줄로 적어라. 못 적으면 소견을 버려라"
5. "한국어로 답하라. 표 형식으로 항목 / 기준선 근거 / 구현 위치 / 상태 / 이슈 를 나열하라"

층별 추가 지시.
- **L1**: 규칙 문서에 명시된 항목만 대상. 취향 문제는 보고하지 않는다
- **L2**: "AI가 임의로 추가한 클래스와 모듈"과 "기존 공통 구조를 우회한 구현"을 별도 항목으로 분리해서 보고
- **L3**: spec의 질문과 답, plan의 목표와 논골을 한 줄씩 훑고 각각 구현에 반영됐는지 대조. **plan의 논골을 넘어 구현된 것(범위 초과)도 ❌로 보고**

### 4층 기동 (메인이 직접 실행)

**단위 테스트 통과를 기동 성공으로 간주하지 않는다.** 컴파일과 단위 테스트는 애플리케이션 컨텍스트를 띄우지 않으므로 생성자 선택, 빈 등록, 설정 바인딩, 마이그레이션 실패를 못 잡는다. 아래 하위 층은 서로 다른 실패를 잡으므로 하나로 다른 하나를 대신하지 않는다.

| 하위 층 | 확인 | 잡는 실패의 예 |
|---|---|---|
| 4a 빌드와 테스트 | 플랜 검증 방법의 빌드, 테스트 명령 | 컴파일 오류, 단위 로직 회귀 |
| 4b 컨텍스트 기동 | 애플리케이션을 실제로 띄우고 기동 완료 로그나 헬스 체크까지 본다 | 의존성 주입 대상 모호, 빈 등록 누락, 설정 키 누락, 마이그레이션 실패 |
| 4c 컨테이너 기동 | 컨테이너나 compose로 배포하는 프로젝트면 그 방식으로 띄운다. 해당 없으면 "해당 없음, 이유" | 이미지 빌드 실패, 환경 변수 누락, 컨테이너 안 경로 차이 |
| 4d 실제 HTTP | 기동한 프로세스에 대표 요청을 실제로 보내 상태 코드와 응답 형태를 spec 계약과 대조한다 | 라우팅 누락, 직렬화 오류, 계약과 다른 응답 필드 |
| 4e 깨끗한 사본 기동 | 아래 명령으로 추적 파일과 무시되지 않은 미추적 파일만 임시 디렉터리에 복사해 4a, 4b를 다시 돌린다 | 로컬 캐시, 무시된 설정 파일, 로컬에만 있는 산출물에 기대는 구현 |

```bash
# 4e: 무시된 파일 없이 현재 작업트리를 복사 (커밋하지 않은 변경 포함)
rm -rf /tmp/fv-clean && mkdir -p /tmp/fv-clean
git ls-files -co --exclude-standard \
  | while IFS= read -r f; do [ -e "$f" ] && printf '%s\n' "$f"; done \
  | tar -cf - -T - | tar -xf - -C /tmp/fv-clean
```

- 기동한 프로세스는 판정 후 반드시 종료한다. 포트를 점유한 채 두지 않는다
- 기동에 실패하면 실패 로그의 첫 원인 줄과 `파일:줄번호`를 보고서에 인용한다
- 명령을 돌리지 못한 하위 층은 🔍로 적고 이유를 쓴다. 돌리지 않은 것을 ✅로 쓰지 않는다
- 4층 결과는 명령 출력이 근거이므로 적대적 필터를 거치지 않는다

## Step 2. 적대적 필터 (배리어)

1~3층 소견을 전부 모아 에이전트 1개에 넘긴다. 층별로 나눠 돌리면 중복과 모순이 안 잡힌다.

```
Agent 호출:
- prompt:
  1. "당신은 적대적 검증 필터다. 아래 각 소견이 틀렸음(오탐/할루시네이션)을 적극적으로 증명하라.
      소견이 지목한 실패 입력이나 경로를 코드나 기준선 문서에서 특정하지 못하면 기본 판정은 ❌ 기각이다."
  2. 1~3층 소견 목록 (각 소견에 층, 파일:줄번호, 기준선 근거 포함)
  3. "필요한 파일만 Read로 확인하라. 전체 diff를 읽지 마라"
  4. "판정: ✅ 확인 / ❌ 기각 / 🔍 불확실. 판정마다 근거 인용 필수"
  5. "여러 층이 같은 코드를 다른 이름으로 지적했으면 중복으로 병합하라"
  6. "층 간 모순(1층은 통과인데 2층이 위반이라고 한 동일 지점)이 있으면 모순으로 표시하라"
  7. "한국어로 답하라"
```

합성 규칙.
| 필터 판정 | 처리 |
|---|---|
| ✅ 확인 | 보고서에 확정 소견으로 기재 |
| ❌ 기각 | 제외. 기각 사유가 부실하면 메인이 재판단 |
| 🔍 불확실 | 메인이 해당 파일만 직접 읽고 유지 또는 기각 결정 |
| 중복 | 하나로 병합, 관련 층을 모두 표기 |
| 모순 | 보고서 별도 섹션에 남기고 사람 판단 대상으로 표시 |

## Step 3. 보고서 작성

경로: `<repo>/.claude/harness/report/verify-<slug>-<YYYYMMDD>.md`. 같은 날 두 번이면 `-2` 접미사.
**이 보고서는 지우지 않는다. 검증을 실제로 돌렸다는 증거로 보존한다.**

```markdown
# 최종 검증 보고서: <slug>

> **작성일**: YYYY-MM-DD
> **검증 대상**: <변경 파일 N개, 기준 커밋 <SHA> 이후 작업트리>
> **기준선**: 1층 <경로> / 2층 <경로> / 3층 <경로 또는 "없음"> / 4층 <기동 명령 출처>

## 요약
| 층 | 기준선 | 확정 소견 | 상태 |
|---|---|---|---|
| 1층 규칙 | <경로> | ❌ N건 / ⚠️ M건 | ✅ 통과 \| ⚠️ 조건부 \| ❌ 실패 \| 🔍 판정 불가 |
| 2층 아키텍처 | <경로> | ... | ... |
| 3층 요구사항 | <경로> | ... | ... |
| 4층 기동 | <명령 출처> | 4a~4e 각 상태 | ... |

## 1층. 규칙 검증
| 항목 | 기준선 근거 | 구현 위치 | 상태 | 이슈 |
|---|---|---|---|---|
| <네이밍 규칙> | `rules.md:41` | `Foo.kt:88` | ❌ | <무엇이 어긋났는가> |

(❌, ⚠️ 항목마다 아래를 붙인다)
**파일**: `<저장소 기준 경로>:<줄번호>` + 문제 코드 블록
**실패 시나리오**: <어떤 입력과 상황에서 무엇이 깨지는가>
**조치**: <구체적 수정 방향>

## 2층. 아키텍처 검증
(동일 형식. 임의 추가 / 공통 구조 우회는 항목을 분리)

## 3층. 요구사항 검증
(동일 형식. spec의 질문과 답 단위로 행을 만든다. 기준선이 없으면 이 절 전체를 "🔍 기준선 부재로 판정 불가"로 적고 원인을 1줄 기재)

## 4층. 기동 검증
| 하위 층 | 실행 명령 | 결과 | 근거(출력 발췌) |
|---|---|---|---|
| 4a 빌드와 테스트 | `<명령>` | ✅ / ❌ / 🔍 | <요약> |
| 4b 컨텍스트 기동 | ... | ... | ... |
| 4c 컨테이너 기동 | ... | ... | ... |
| 4d 실제 HTTP | ... | ... | ... |
| 4e 깨끗한 사본 기동 | ... | ... | ... |

## 층 간 모순 (있을 때만)
| 지점 | 층 A 판정 | 층 B 판정 | 사람 판단 필요 사항 |

1. **<제목>** / `<파일>:<줄>` / 사유: <1줄> / 회귀 단계: 요구사항 \| 플래닝 \| 구현

## 판정
✅ 종료 가능 / ⚠️ 조건부 종료(조치 후 재검증) / ❌ 회귀 필요 → <요구사항, 플래닝, 구현 중 어디>
```

## Step 4. 판정과 회귀

| 조건 | 판정 | 다음 |
|---|---|---|
| 확정 ❌ 0건이고 4층 4a, 4b, 4d가 ✅ | ✅ 종료 가능 | 작업 종료 |
| ❌ 있으나 1, 2층뿐 | ⚠️ 조건부 | 수정 후 해당 층만 재검증 |
| 4층에 ❌ (빌드, 기동, 응답 실패) | ❌ 회귀 | 구현 단계로 되돌린다. 기동이 안 되는 작업은 다른 층이 전부 ✅여도 종료하지 않는다 |
| 4층이 🔍 (기동 명령 부재, 실행 불가) | ⚠️ 조건부 | 기동 명령을 확보해 4층만 재검증 |
| 3층에 ❌ (기능 누락, 범위 이탈) | ❌ 회귀 | 요구사항 단계 또는 플래닝 단계로 되돌린다 |
| 3층 🔍 판정 불가 | ❌ 회귀 | spec 작성부터 다시 |

3층 실패는 코드를 고쳐서 닫지 않는다. 요구사항이나 플랜이 틀렸다는 신호이므로 그 문서부터 고친다.

## 토큰 규율과 주의사항

- diff는 `/tmp/fv-diff.txt` 로 한 번만 저장하고 메인과 에이전트가 Read로 공유한다. 프롬프트 복붙 금지
- 각 층 에이전트에게 전체 diff를 주지 않는다. 변경 파일 목록과 담당 기준선만 준다. 필터 에이전트에게는 소견 목록만 준다
- 기준선 문서가 200줄을 넘으면 메인이 관련 절만 발췌해 전달한다
- 변경 파일이 3개 이하면 에이전트를 띄우지 않고 메인이 1~3층을 직접 훑는다. 4층은 변경 크기와 상관없이 항상 돈다
- 보고서는 한국어. 상태 마커와 `파일:줄번호`는 필수. 근거를 인용하지 못하는 소견은 넣지 않는다
- 커밋과 푸시는 하지 않는다. 판정만 한다. 커밋 전 diff 리뷰는 `review-gate` 담당이다
